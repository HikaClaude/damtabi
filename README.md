# ダム旅 / DAM TABI

**旅の寄り道に、ダムなんていかが？**

ダムを地図から探して、知って、実際に見に行くためのアプリです。当面は富山県の23基が対象。

バッチ（Python）が国土交通省「川の防災情報」から貯水状況を取得して `docs/data/dams.json` に
書き出し、SPA（MapLibre GL JS ＋ 地理院タイル）がそれを読んで表示します。サーバレスの静的サイトです。

| | |
|---|---|
| アプリ名 | ダム旅（DAM TABI） |
| 制作名義 | DAM TABI LAB |
| 公開URL | https://damtabi.com |
| 対象 | 富山県の23基（将来的に全国へ拡張予定） |

> **名称について**：「ダム旅」は一般的な表現でもあります。名称の独占性ではなく
> 「見ただけで意味が伝わること」を優先して採用しました。サービスとしての固有性は
> ダム旅 / DAM TABI・DAM TABI LAB・ロゴ・アイコン・オリジナルのダムイラスト・UI の
> 組み合わせで作っていきます。

## いちばん大事な原則

> **取れなかったデータは「取れなかった」と表示する。**

推定値で埋めない。前回値を使い回さない。片方の貯水率でもう片方を代用しない。
値が無いときは `—` を出し、**なぜ無いのか**を必ず添えます。

理由は 5 種類に分けています。

| status | 表示 | 意味 | 今日の該当 |
|---|---|---|---|
| `ok` | 数値 | 取得できた | 15 基 |
| `missing` | — 欠測 | 観測所からデータが届いていない | 熊野川・朝日小川 |
| `not_provided` | — 未提供 | その観測所ではその項目を公表していない | 刀利・五位・臼中 |
| `closed` | — 閉局 | 観測を行っていない | （現在なし） |
| `fetch_failed` | — 取得失敗 | 通信・サーバ側の問題で取れなかった | （現在なし） |
| `no_source` | — データ提供なし | そもそも公開している事業者がいない | 黒部・有峰・出し平 |

判定はダム単位ではなく**項目単位**です。たとえば熊野川ダムは貯水位（313.14 m）は取得できて
貯水量・貯水率だけが欠測なので、貯水位は数値を出し、貯水率だけ「— 欠測」と出します。

## 運用方針：更新は手動で行う

**このアプリは自動更新しません。更新は人が手で実行します。これが正規の運用です。**

川の防災情報の[取り扱い上の注意](https://www.river.go.jp/kawabou/kwb_apend/html/caution.html) 1.2) に、
ツール等による**定期的な**データ収集は控えるよう明記されているためです（詳細は次節）。
定期実行（cron）は意図的に無効にしてあり、人が判断して実行する形にしています。

### 更新のしかた

```bash
# 1) 貯水率を取得して docs/data/dams.json を作り直す
python scripts/fetch_dams.py

# 2) ダムごとの静的ページ・sitemap・manifest を作り直す
python scripts/build_site.py

# 3) 公開（GitHub Pages なら push するだけ）
git add docs/data/dams.json docs/dam docs/index.html docs/sitemap.xml docs/robots.txt docs/manifest.json
git commit -m "data: 貯水率を更新"
git push
```

GitHub 上で実行したい場合は、Actions タブから `fetch-dams` ワークフローを
**Run workflow** で手動起動しても同じことができます（cron は無効のままです）。

### 更新のタイミングの目安

| 状況 | 目安 |
|---|---|
| 通常時 | **週1〜2回**。渇水期・出水期は多めに |
| 渇水のニュースが出たとき | その都度 |
| 大雨・台風の前後 | 更新するより、利用者を[川の防災情報](https://www.river.go.jp/kawabou/pcfull/tm)へ誘導するのが適切 |
| イラストを追加したとき | `make_images.py` も実行（貯水率の取得は不要） |

**防災用途はこのアプリの守備範囲ではありません。** 出水時のリアルタイム性が要る場面では
川の防災情報を見てもらう前提で、各ダムのページに公式ページへのリンクを置いてあります。

1回の実行で相手サーバに出すリクエストは **約21件**です（観測所マスタはローカルにキャッシュ済み）。

### 貯水率が取れなくても壊れない

手動運用では更新が数日空きます。そのため「いつの値か」の見せ方を作り込んであります
（→「古い値を現在値に見せないための仕組み」）。
また、全基が取得不可になってもアプリは成立します（`data_status` の `no_source` 扱い）。

## ⚠ データ取得の利用条件

**現在の取得方式は、川の防災情報の利用条件上「お控えください」と明記された行為に該当します。**
上記のとおり**定期実行をやめて手動運用にする**ことで当面の折り合いをつけていますが、
FRICS への照会結果によっては経路の変更が必要になります。

### 何が書かれているか

[取り扱い上の注意](https://www.river.go.jp/kawabou/kwb_apend/html/caution.html) の 1.2)（原文）:

> 当ホームページは一般の方々が通常のブラウザで閲覧されることを前提に情報を掲載しています。
> **ツール等による定期的なデータ収集は、サーバに過度の負担がかかりサービス提供に支障をきたすため、
> お控えいただきますようお願いいたします。**
> 商用・非商用を問わず、定期的・定常的なデータ収集を行われる場合は、以下に記載するリンク先ページより
> データ配信を受けることができますのでご利用ください。
> ・河川情報数値データ配信事業 https://www.river.or.jp/koeki/opendata/index.html
> なお、一定期間の通信量が著しく多い場合や高頻度のアクセスが確認された場合、
> 利用元に対してアクセス制限を行う場合があります。

姉妹サイトの[水文水質データベース](http://www1.river.go.jp/caution.html)にも同趣旨の記載があります
（「ツール等による、自動的なデータ収集等は…原則としてご遠慮ください」）。
**無料で自動取得してよい公式経路は見つかりませんでした。**

問題になっているのは「定期的・定常的」であることなので、
**cron を止めて人が都度実行する形にし、リクエスト数も削減**しています。
これで完全に白と言い切れるわけではありません。判断の分かれ目なので、FRICS へ照会中です。

### データそのものの利用は問題ない

取り扱い上の注意 2. は明確です。

- コンテンツは**複製・公衆送信・翻案等が自由**、**商用利用も可**
- **数値データは著作権の対象ではない**ため、そもそも本ルールの適用外で自由に利用できる
- 政府標準利用規約（第2.0版）準拠、**CC BY 4.0 と互換**
- 出典の記載が必要。記載例は「出典：国土交通省　川の防災情報ホームページ（当該ページのURL）」、
  加工した場合は「国土交通省　川の防災情報ホームページ（URL）を加工して作成」

→ **問題は「データを使うこと」ではなく「自動で定期的に取りに行くこと」だけ**です。

### 正式な代替手段と費用（照会中）

**水防災オープンデータ提供サービス（河川情報数値データ配信事業）** — 一般財団法人河川情報センター
（FRICS）が国交省の事業として配信。テレメータ「ダム諸量」に貯水位・貯水量等が含まれます。

| 項目 | 単位 | 月額（税抜） |
|---|---|---|
| ダム諸量（国所管） | 地方整備局ごと | 2,100円 |
| ダム諸量（都道府県所管） | 都道府県ごと | 2,100円 |
| 通信回線負担金（インターネット回線） | 一式 | 9,600円 |

- **富山県だけの場合**：北陸地整 + 富山県 + 回線 = **月 13,800円（税抜）／年 約18万円**
- **全国に広げた場合**：10地整 + 47都道府県 + 回線 = **月 約129,300円（税抜）／年 約155万円**
- **プッシュ型の配信**なので受信側にサーバが要り、現在のサーバレス構成が崩れます。
- 申込書・契約が必要（問い合わせ: haisin-info@river.or.jp）

照会内容の案：「非商用の観光情報アプリ「ダム旅」。富山県内20観測所、更新は手動で週1〜2回、
1回あたり約21リクエスト。この程度でも配信契約が必要か、Web取得が許容される条件があるか」。

### 参考: 他の経路

- **ダム諸量データベース**（[mudam.nilim.go.jp](https://mudam.nilim.go.jp/home)、国総研）
  国・水機構・都道府県のダムの**統計値**を公開。平成5年以降。ただし
  **貯水率は項目に無く**（貯水位・流入量・放流量・水温・濁度・水質）、リアルタイムでもないため
  現在値には使えません。ただし**平年値の算出には有力**なので、閾値設計を見直すときの候補です。
- **富山県の公表**：土木部所管16ダムの貯水率は報道発表PDFで不定期に出るのみ。機械可読な定期配信なし。
- **富山防災WEB**：貯水位のみ。貯水率・貯水量なし（16基）。

## 使い方

更新の手順は「運用方針」に書いたとおりです。ここでは補足だけ。

```bash
# ローカルで表示（file:// では fetch できないので簡易サーバを使う）
cd docs && python -m http.server 8765
# → http://127.0.0.1:8765/
```

`docs/` をそのまま GitHub Pages / Netlify / S3 などに置けば動きます。ビルド不要、API サーバ不要。

### 公開URLの設定は `site.json` の 1 行だけ

```json
{ "base_url": "https://your-domain.example/dam-map", ... }
```

ここを書き換えて `build_site.py` を実行すれば、
**canonical / og:url / og:image / sitemap.xml / robots.txt / manifest.json / 地図画面のメタ**が
すべて追随します。独自ドメインへの移行もこの 1 行です。

地図画面（`docs/index.html`）は手書きの HTML ですが、URL に依存するメタだけは
`<!-- BEGIN generated-site-meta -->` 〜 `<!-- END generated-site-meta -->` で囲ってあり、
その中身を `build_site.py` が生成します。二重管理になりません。
（`--base-url` 引数と環境変数 `SITE_BASE_URL` でも一時的に上書きできます。）

アイコンと OGP 画像は**単発**スクリプトで作ります（毎回の更新では不要）。

```bash
python scripts/make_images.py          # アイコン + 全ダムのOGP画像
python scripts/make_images.py --icons-only
```

ローカルの Chrome / Edge のヘッドレスでラスタライズします（画像ライブラリ不要）。
生成物は日々変わる数値を含まないので、そのままコミットして使い回せます。

`.github/workflows/fetch-dams.yml` は**手動起動（workflow_dispatch）専用**にしてあります。
cron はコメントアウトしてあり、理由もファイル内に書いてあります。

### URL で状態を共有できる

- `#dam_id=toyama-unazuki` … そのダムの詳細を開いた状態で開く（新しく書き出すリンクはこの形。同名ダムがあっても取り違えない）
- `#dam=宇奈月ダム` … 旧形式。今も開ける。同名のダムが複数あれば候補一覧を出し、どれも自動で選ばない
- 知らない ID・矛盾した指定は、別のダムへ代わりに飛ばず「見つかりませんでした」と出す
- `#basis=effective` … 有効貯水率で色分けした状態で開く

`app.js`・`style.css`・`page.css`・`sw.js`・集水域の索引の版が変わると、`scripts/build_site.py` が
内容から版（`?v=…` と Service Worker の `VERSION`）を付け直す。手で版を上げる必要はない。

## 出典表記

画面上に**常時表示**しています（地図画面はヘッダ内の 1 行、各ページはフッタ）。

> 出典：国土交通省　川の防災情報ホームページ を加工して作成 ／ 地図：地理院タイル（国土地理院）

- **国土交通省**：[取り扱い上の注意](https://www.river.go.jp/kawabou/kwb_apend/html/caution.html) 2.1)
  の記載例どおりの文言にしています。数値を JSON に再構成しているので、同 2.1)イ に従い
  「加工して作成」も明示しています（リンク先が「当該ページのURL」に当たります）。
- **国土地理院**：地理院タイルは「国土地理院」または「地理院タイル」と記載し、
  [地理院タイル一覧ページ](https://maps.gsi.go.jp/development/ichiran.html)へのリンクを付けることが
  求められています。両方満たしています。ウェブサイトからのリアルタイム読み込みは申請不要です。

地図画面では MapLibre 内蔵の attribution コントロールを CSS で隠し、自前の表示に置き換えています。
出典をヘッダの中に置いたのは、**詳細パネルにも凡例にも決して隠されない場所がそこだけ**だからです
（地図の右下に置くと、詳細パネルを開いたときに覆われてしまう）。

内蔵の attribution コントロール自体は削除せず CSS で隠すだけにしています。
`attributionControl: false` を指定すると MapLibre GL JS 4.7.1 では `load` イベントが発火せず、
地図が描画されなくなるためです（実測して確認）。

なお地図のピンは `load` を待たずに配置しています。ピンは DOM オーバーレイなので
スタイルの読み込みを待つ必要がなく、**タイルが出ない状況（オフライン・タイル配信の不調）でも
ダムの位置と貯水率は読める**ようにするためです。

## 発見性（SEO / SNS / PWA）

### ダムごとの静的ページ

`/dam/{slug}/` にダム 1 基 = 1 枚の HTML を生成します。**値はサーバ側（バッチ）で埋め込み済み**で、
JavaScript なしでも本文が読めます。

- `title` と `meta description` はダムごとに個別。ダム名・所在地・水系・その日の貯水率を含みます
- `canonical` / OGP / Twitter Card / JSON-LD（`Place` と `BreadcrumbList`）を各ページに付与
- `sitemap.xml`（全 25 URL）と `robots.txt` を自動生成
- 地図のピンをタップ → 詳細パネルの「◯◯ダムの詳細ページ →」から遷移
- ヘッダの「ダム一覧」から `/dam/` の一覧ページへ。一覧から各ページへ内部リンク
- 各ページから「地図でこのダムの位置を見る →」で `#dam_id=◯◯` 付きの地図へ戻る

### URL 設計（全国化しても壊れないように）

URL は **`/dam/{都道府県}/{読みのローマ字}/`** です（`/dam/toyama/unazuki/`、`/dam/toyama/kadokawa/`）。
数値の観測所コードではなく読みにしたのは、検索結果や SNS で意味が読み取れるほうが発見性に効くためです。

**都道府県を挟んでいるのは、全国化したときの同名衝突を今のうちに避けるため**です。
ダム名の重複は例外ではなく前提で、たとえば大谷ダムは富山県のほかに新潟県にもあります。
県セグメントが無いと全国化の時点で URL の作り直しが要りますが、それは
「すでに検索エンジンに拾われた URL を壊す」というSEO上いちばん高くつく作業です。
市町村ではなく都道府県にしたのは、市町村合併では変わるが都道府県は実質変わらないためです。

安定キーの持ち方は次のとおりです。

- `dam_slugs.csv`（`dam_name, pref, slug`）が**唯一の対応表**で、リポジトリ内で手管理します。
  データ源の仕様が変わっても、ここを触らない限り URL は変わりません。
- `dams.json` の `id` は `toyama-unazuki` の形。**取得元の観測所コードに依存しない自前のキー**で、
  イラストの割り当て（`illustrations.json`）と OGP 画像のファイル名にも同じ id を使います。
- 取得元固有のコード（13桁の `obsFcd`）は `obs_fcd` / `source` に分けて持っています。
  川の防災情報をやめても、URL とイラストの紐付けは影響を受けません。

読みは川の防災情報のマスタ（`obsKana`）で確認済みです（角川ダム＝かどかわ、舟川ダム＝ふながわ など）。

### OGP

- トップと一覧：`docs/img/og/site.png`
- 各ダムページ：`docs/img/og/{id}.png`（ダム名・水系・所在地入りの 1200×630）

OGP 画像には**日々変わる数値を入れていません**。SNS 側は画像を長期キャッシュするので、
古い数値が貼り付いたまま残るのを避けるためです。数値は `og:description` に入れて毎日更新します。

**イラストができたら OGP は自動で差し替わります。** ダムごとに OGP を手作りする必要はありません。

1. 3:2 のイラストを `docs/img/dams/` に置く
2. `docs/data/illustrations.json` にダムID（`toyama-unazuki` 等）で登録する
3. `python scripts/make_images.py` を実行する

`make_images.py` が 3:2 のイラストを 1200×630 に `object-fit: cover` で切り出し、
下部にグラデーションを重ねてダム名・水系・所在地を載せた OGP 画像を作ります。
同じ `illustrations.json` を地図の詳細パネルとダムページも見ているので、
**登録は1箇所だけ**で地図・静的ページ・OGP の3か所に反映されます。

### Google Search Console

アクセス把握は **Search Console だけ**にしている。サイトに計測コードを置かないので、
利用者の端末から外部へ余計なリクエストが出ない。「追跡しない」方針と矛盾しない唯一の手段。

独自ドメインへ移行したので、**ドメインプロパティ（DNS の TXT レコード認証）が使える**。
`damtabi.com` の DNS は Cloudflare にあるので、そこに TXT を 1 件足すだけで済む。
（移行前は `github.io` が Public Suffix List に載っているためドメインプロパティを作れず、
URLプレフィックス＋HTMLファイル方式しか選べなかった）

1. Search Console で「ドメイン」を選び `damtabi.com` を入力
2. 表示された TXT レコードを Cloudflare の DNS に追加（名前 `@`、値 `google-site-verification=...`）
3. 「確認」を押す。DNS 反映は数分
4. 「サイトマップ」に `https://damtabi.com/sitemap.xml` を送信（25URL）

ドメインプロパティなら `www` も `http` も `https` もまとめて 1 つのプロパティで見られる。

旧プロパティ（`https://hikaclaude.github.io/damtabi/`）を既に作ってある場合は**消さない**。
301 リダイレクトが認識され評価が新ドメインへ移るまで数週間かかるため、両方残しておく。

HTMLファイル方式を使う場合は、`googleXXXX.html` を **`docs/` 直下に置いて** commit → push する
（`build_site.py` は `index.html` / `manifest.json` / `sitemap.xml` / `robots.txt` しか書かないので
消えない。`.gitignore` にも掛からない）。

metaタグ方式を使いたい場合は、`site.json` の `google_site_verification` に content の値を入れて
`build_site.py` を実行すれば `docs/index.html` に出力される（空なら何も出さない）。

見えるようになるのは、検索クエリ別の表示回数・クリック数・平均掲載順位、ページ別の同データ、
インデックス登録状況とエラー、モバイルユーザビリティ、被リンク。すべて Google 側の集計。

### PWA

`manifest.json` と `sw.js` を用意してあり、ホーム画面に追加できます。

- アイコン：192 / 512 / maskable 512 / apple-touch 180 と SVG
- Service Worker の原則は**「貯水率が載っているものは必ずネットワーク優先」**です。
  貯水率は JSON だけでなく**静的HTMLにも埋まっている**ので、
  HTML もキャッシュ優先にすると古い値を現在値として見せてしまいます。そのため
  **`data/*.json` と HTML ページは両方ネットワーク優先**、
  CSS / JS / 画像 / アイコンだけキャッシュ優先にしています。
- 通信できずキャッシュを返すときは、必ず古いと分かるようにします。
  - JSON … `stale` フラグを立て、地図の見出しに「オフライン: 保存済みの内容を表示中」
  - HTML … `<!--STALE-SLOT-->` を警告バーに差し替えて
    「オフラインのため、端末に保存された内容を表示しています」と表示

## 古い値を現在値に見せないための仕組み

このアプリで最も壊してはいけないところです。**手動更新なので更新が数日空きます。**
そのぶんここを厚くしてあります。

### 4層で守る

1. **欠測・未提供は埋めない**（バッチ）。前回の JSON を読まないので、値の流用が構造的に起きません。
2. **「いつの値か」を数値のすぐ下に必ず出す**。閾値はありません。常に出ます。
   - JS なしでも本文に `2026年9月4日 21:10 観測の値です（このページの生成: … JST）` と書いてあります
   - JS が動けば `（約3日前の観測値です）` という**経過日数**が加わります
3. **通常の更新リズムを超えたら段階的に注意を強める**（下記）。
4. **オフラインキャッシュは古いと明示する**（Service Worker）。

### 警告を出す日数と、その根拠

`site.json` の `freshness` で設定します。既定は **注意 7日 / 警告 14日**です。

| 経過 | 表示 |
|---|---|
| 常時 | 観測日時＋経過日数（例: 約3日前の観測値です） |
| **7日**以上 | 橙の注意「最新の貯水率は変わっている可能性があります」＋川の防災情報へのリンク |
| **14日**以上 | 赤の警告「大きく変わっている可能性があります」＋同リンク |

**なぜ 24 時間ではなく 7 日にしたか。**

最初は 24 時間で警告を出していましたが、手動運用では数日空くのが常態です。
**通常運用のたびに警告が出ると、利用者は警告を読み飛ばすようになります。**
そうなると本当に古いときにも効かなくなり、かえって原則を損ないます。

代わりに **経過日数そのものを閾値なしで常時表示**しました。
これで「黙って古い値を見せる」状態は日数によらず発生しません。
警告バーの役割は「値の開示」ではなく「通常の更新リズムを超えた」という一段上の合図に絞りました。

7日という数字は実測から決めています。手元の実測（室牧ダム、渇水期の低下局面）で
**利水貯水率は 9/1 の 68.1% から 9/4 に 60.8%、3日で 7.3ポイント（約 −2.4pt/日）**動きました。
この速さだと

| 経過 | 変化量の目安 |
|---|---|
| 3日 | 約 7ポイント |
| **7日** | **約 17ポイント** |
| 14日 | 約 34ポイント |

7日で約17ポイント。これは**このアプリの色分け1段ぶん**（80–95%、60–80%、40–60% はいずれも15〜20ポイント幅）に相当します。
つまり 7日経つと「地図上の色が変わっていてもおかしくない」水準です。注意を出す線として妥当と判断しました。
14日は約34ポイントで2段ぶん、これは警告に値します。

なお最上位の「95%以上」帯は5ポイント幅しかなく、この速さなら約2日で外れる計算です。
ただし帯の色分けは地図側の話で、静的ページが見せるのは日付つきの数値です。
そこは常時表示の経過日数でカバーしています。

**更新頻度を変えたら閾値も変えてください。** 毎日自動更新に戻すなら
`notice_days: 2 / warn_days: 5` あたりが目安です（`site.json` の1箇所）。
地図と静的ページは同じ設定値を見るので、基準がずれることはありません。

## 取得経路の選定

4 つの候補を実際に叩いて比較しました。結論は **「川の防災情報」の静的 JSON** です。

### 候補の比較

| 経路 | 利水貯水率 | 有効貯水率 | 形式 | 認証 | 判定 |
|---|---|---|---|---|---|
| **川の防災情報 静的 JSON** | ○ | ○ | JSON | 不要 | **採用** |
| www1.river.go.jp `DspDamData.exe` | △ 1 種のみ | × | EUC-JP の HTML | 不要 | 不採用 |
| dam.teraren.com API | ○ | ○ | JSON | **APIキー必須** | 不採用 |
| 富山防災WEB 実況表 | × | × | HTML | 不要 | 不採用 |

### なぜ「川の防災情報」の静的 JSON なのか

river.go.jp は Vue の SPA で、画面は JS 描画です。ただし**描画に使っている実データは
ただの静的 JSON ファイル**で、そこを直接読めば JS 実行なしで取得できます。

```
最新観測時刻  https://www.river.go.jp/kawabou/file/system/tmCrntTime.json
観測所マスタ  https://www.river.go.jp/kawabou/file/files/master/obs/dam/{obsFcd}.json
時系列データ  https://www.river.go.jp/kawabou/file/files/tmlist/dam/{YYYYMMDD}/{HHmm}/{obsFcd}.json
```

`obsFcd` はサイトの `app.js` と同じ規則で組み立てます（13 桁）。

```
("0000"+ofcCd).slice(-5) + ("00"+itmkndCd).slice(-3) + ("0000"+obsCd).slice(-5)
ダムの itmkndCd は 7。例) 室牧ダム = ofc 4098 / obs 63 → 0409800700063
```

採用した理由は 4 つです。

1. **両方の貯水率が別フィールドで取れる唯一の無認証経路**
   `storPcntIrr`（貯水率利水容量）と `storPcntEff`（貯水率有効容量）が独立して入っています。
2. **欠測と未提供を機械判定できる**
   各値に `*Ccd`（品質コード）が付きます。サイトの `app.js` と同じ規則で解釈しています。
   `190` = 欠測、`140` = 閉局、`130 以上または null` = その観測所では未提供、それ未満 = 有効な値。
   **推測せずに「取れない理由」を出せる**のはこの経路だけでした。この要件にとっては決定的です。
3. **JSON なのでスクレイピングより壊れにくい**
   HTML 構造の変更に影響されません。文字コードの問題もありません（UTF-8）。
4. **任意時刻を指定して取り直せる**
   `tmlist/dam/20260901/2020/...` のように過去のスロットも実在します（**約 1 か月**保持。
   8 日前は取得可、1 か月前は 404 を確認）。最新スロットが未生成のときに 10 分ずつ遡れるので、
   「一時的にファイルが無いだけ」を「欠測」と誤って記録せずに済みます。

なお river.go.jp の JS には `location.origin + "/api"` を叩く REST 実装も残っていますが、
本番では全て 404 でした（`Cannot GET /kwb/api/...`）。使われていない実装なので採用していません。

### 落選した経路の理由

**www1.river.go.jp（水文水質データベース）の `DspDamData.exe`**
現役で応答します（EUC-JP の HTML テーブル）。ただし返る貯水率カラムは**1 種類だけ**で、
利水と有効を併記できません。この要件（4 倍違うのでどちらかに丸めない）を満たせないので不採用。
HTML スクレイピング＋EUC-JP デコードが必要で、`.exe` CGI という壊れやすさもあります。

**dam.teraren.com**
API は `https://dam.teraren.com/api/v1/` に実在し、19 年分の履歴を持ち、利用は無償です。
ただし **Google サインインで発行する API キーが必須**で、認証情報なしのサーバレス日次バッチには
組み込めません。加えてサイト自身が「観測値のリアルタイム提供は行っていません」と明記しており、
出典も国交省の公開データです。**一次情報を直接取れるなら一次情報を取るべき**なので不採用。
ただし後述の平年値を作るときの有力候補なので、README に残しておきます。

**富山防災WEB（bousai.pref.toyama.jp）**
サーバレンダリングで扱いやすいのですが、実況表のカラムは
`ダム名 / 水系名 / 全流入量 / 全放流量 / 貯水位 / 洪水調節容量の各水位` で、
**貯水率も貯水量もありません**。掲載は県土木部管理の 16 基のみ（宇奈月・刀利・五位・臼中を含まない）。
このアプリの主目的を満たせないので不採用。

**第三者の個人サイト**
方針どおりスクレイピング対象にしていません。

## ピンの色分けと閾値の設計

### 問題

利水貯水率を等分割（0-33 / 34-66 / 67-100 など）で塗ると、ほとんどが同じ色になります。
実測（2026-09-04 20:30 時点、値が取れた 15 基）でも **6 基がちょうど 100.0%**、
99.2% を足すと **7 基が最上位バケットに集中**します。

### 原因は運用であって、データの不備ではない

観測所マスタの `lmtStg1`（洪水期制限水位）と運用期間を突き合わせると理由が見えます。
洪水期のダムは、洪水にそなえて水位を制限水位まで下げて運用します。このとき

- **利水容量**（利水のために確保する下側の容量）は満杯 → 利水貯水率 **100%**
- **有効容量**（利水容量＋洪水調節容量）は上側が意図的に空 → 有効貯水率は**低い**

という状態が「正常」になります。大谷ダムが典型で、制限水位 143.6 m に対して実測 143.71 m、
結果は**利水 100.0% / 有効 5.2%（約 19 倍差）**。CSV の備考「有効貯水率が極端に低い」は
故障ではなく設計どおりの運用状態です。

つまり **2 つの貯水率は別のことを測っている**ので、片方に丸めてはいけません。

- 利水貯水率 = **使える水がどれだけ残っているか**（渇水の指標）
- 有効貯水率 = **容量全体のうちどれだけ埋まっているか**（洪水期は低いのが正常）

### 平年値との乖離で色を決める案について

検討しましたが、**今回は採りませんでした**。

- 川の防災情報のマスタには基準値フィールド（`storPcntBs` / `storPcntEffBs`）がありますが、
  富山県の 20 基すべてで `null` でした。平年値は入っていません。
- 時系列 JSON の保持期間は**約 1 か月**で、平年値を作るには全く足りません。
- 19 年分の履歴を持つ dam.teraren.com は API キーが必要で、初版の前提（認証なし・サーバレス）に合いません。

**入手できない基準値をアプリ側で推定して色を決めるのは、このアプリの原則に反します。**
そこで固定閾値にしましたが、等分割ではなく次のように設計しました。

### 採用した閾値

**利水貯水率（既定）— 「満水からどれだけ目減りしたか」を見る非線形の刻み**

100% 付近が常態なので、上側を細かく、下側を粗く切ります。

| 区分 | 色 | 今日の該当数 |
|---|---|---|
| 95% 以上（ほぼ満水） | 青 `#1d4ed8` | 7 |
| 80–95% | 水色 `#0891b2` | 2 |
| 60–80% | 緑 `#15803d` | 2 |
| 40–60% | 橙 `#ea9a1a` | 2 |
| 40% 未満（少ない） | 赤 `#dc2626` | 2 |

7 / 2 / 2 / 2 / 2 に分かれ、5 色すべてが実際に使われます。
「95% 未満に落ちたら目に留まる」という、渇水の指標としての意味も持たせています。

**有効貯水率（切替可）— 実分布に合わせた刻み**

実測レンジが 2.0–51.6% と低い側に寄るので、閾値も低い側に寄せます。

| 区分 | 色 | 今日の該当数 |
|---|---|---|
| 60% 以上 | 青 | 0 |
| 40–60% | 水色 | 2 |
| 25–40% | 緑 | 6 |
| 10–25% | 橙 | 5 |
| 10% 未満 | 赤 | 2 |

**データなし**は色ではなく**斜線ハッチのグレーピン**にして、値が低いのか無いのかを取り違えないようにしています。

### 誤読を防ぐための表示

洪水期にあたるダムでは、詳細パネルに

> 現在は洪水期（03/21〜11/30）。洪水にそなえて水位を制限水位（143.6m）まで下げて運用するため、
> 利水貯水率が高くても有効貯水率は低く出ます。異常ではありません。

と出します。運用期間はマスタの `lmtStgStrt1` / `lmtStgEnd1` から取っています。

閾値は `scripts/fetch_dams.py` の `THRESHOLDS` に定義され、`dams.json` に書き出されます。
**SPA は自分で閾値を持たず JSON を読むだけ**なので、変更は 1 か所で済みます。

## イラストの差し込み

イラストは **2 種類**あります。用途が違うので、どちらも同じダムIDで持ちます。

| 種類 | 置き場所 | 形 | 使われ方 |
|---|---|---|---|
| **カード** | `docs/img/dams/` | 3:2（1200×800） | 地図の詳細パネル、静的ページ、OGP の元画像 |
| **アイコン** | `docs/img/dam-icons/` | 正方形（512×512） | 地図ピンの中身 |

ピンにカードを使うと、丸く切り抜いたときに左右が落ちて何のダムか分からなくなります。
そのためピン専用に正方形で描き起こしたものを別に持っています。
アイコンが無いダムはカードで代用し、それも無ければ従来どおり数字だけのピンになります。

富山23基の画像は `dam-image-pipeline`（実物写真の調査 → 生成 → 独立QA → Web用書き出し）で
制作したもので、**Web配信用に書き出した派生物だけ**をこのリポジトリに置いています。
高解像度マスター（1枚 3MB 前後）はリポジトリに含めません。

### 1. 画像を置く

```
docs/img/dams/toyama-unazuki.webp        カード（3:2）
docs/img/dam-icons/toyama-unazuki.webp   アイコン（正方形）
```

**ファイル名はダムID（`dams.json` の `id`）と同じ英数字**にしてください。
サイズは **3:2**（900x600 以上を推奨）。png / jpg / webp が使えます。

> **日本語ファイル名でも動作します**（配信・相対パス解決・OGP生成すべて確認済み）。
> それでも英数字を推奨する理由は次の 3 つです。
>
> 1. URL では `%E5%AE%87...` のようなパーセントエンコードになり、
>    ログやSNSのデバッガで何の画像か読めない
> 2. Windows / macOS / Linux で濁点の正規化（NFC / NFD）が食い違い、
>    「ローカルでは出るのに GitHub Pages で 404」が起きうる
> 3. ダムID と同じ名前にしておけば、`illustrations.json` を見なくても
>    どのダムの画像か一目で分かり、OGP の出力ファイル名とも揃う

### 2. マニフェストに登録する

カードは `docs/data/illustrations.json`、アイコンは `docs/data/dam-icons.json` です。
書式は同じで、キーは **ダムID**、値は **`docs/` ルート基準のパス**です。

```json
// docs/data/illustrations.json
{ "toyama-unazuki": "./img/dams/toyama-unazuki.webp" }

// docs/data/dam-icons.json
{ "toyama-unazuki": "./img/dam-icons/toyama-unazuki.webp" }
```

パスは必ず `./img/...` の形で書いてください。
ダムページは 3 階層下にあるため、ビルド時に `../../../img/dams/...` へ自動変換されます。
アイコンは地図画面だけが読むので、この変換は不要です。

（キーにはダム名も使えますが、改名の影響を受けないIDを推奨します）

### 3. 反映する

```bash
python scripts/build_site.py    # 静的ページに反映
python scripts/make_images.py   # OGP画像を作り直す
```

地図画面は `illustrations.json` を実行時に直接読むので、再ビルド不要です。

### 反映先

| 反映先 | 使う画像 | 使われ方 |
|---|---|---|
| 地図ピン | アイコン | 貯水率の円弧と数字はそのまま。円の内側にアイコンを敷き、数字は下部に白抜きで重ねる |
| 地図の詳細パネル | カード | 上部のイラスト枠 |
| ダムごとの静的ページ | カード | 同じくイラスト枠 |
| OGP 画像 | カード | 3:2 から 1200x630 を `object-fit: cover` で切り出し、ダム名・水系・所在地を重ねて自動生成 |

**画像はピンの一覧性を壊しません。** 円弧の長さと色（残量の二重符号化）、
中央の数字、データなしの「—」表示はイラストの有無にかかわらず同じです。

どちらのマニフェストもバッチが上書きしません。**貯水率を再取得してもイラストの割り当ては消えません。**
未登録のダムは、これまでどおり汎用の OGP カードと「イラスト準備中」のプレースホルダになります。

### QA が未了の3基（公開前に人が見る）

富山23基のうち **20基は独立QAで PASS**、**3基は `NEEDS_HUMAN_REVIEW` のまま**です。
表示できる状態にはしてありますが、**QAは解決していません**。公開前に人の目で判断してください。

| ダム | 指摘 |
|---|---|
| 上市川第二ダム | カードの洪水吐上部に**文字のように見える描き込み**が残る（画像内に文字を入れない規約に触れる可能性） |
| 久婦須川ダム | アイコンの上段開口が5つに見え、実物の設備配置と一致しない |
| 宇奈月ダム | 排砂・ゲート・塔屋群の配置を、公式配置図か独立した航空写真で最終照合する余地がある |

この3基は Web書き出しのPASSゲートで除外されるため、派生物はマスターから
`optimize_images.py` で同じ寸法（カード1200×800 / アイコン512×512）に変換して置いています。

### 証拠層と評価区分（全国化に向けた、人手監査への振り分け）

品質ゲート（上）は「配信してよいか」を止める仕組みで、「集水域そのものが正しいか」は保証しない
（`exact` の輪では輪と雨マスクは自明に一致する。面積の照合は便覧のある基だけ）。
全国化で正常群を自動でふるい分け、異常だけを人手監査へ送れるよう、**判定の材料になる観測値を
dam_id ごとに記録する層**を別に持つ。`scripts/ws_evidence.py`（純関数）・`scripts/ws_outlet_profile.py`
（出口周辺の面積プロファイル）・`scripts/ws_eval_summary.py`（集計）。

```bash
python scripts/ws_outlet_profile.py --basins-dir <build_basins の出力> --out profiles.json --workers 4   # 標高キャッシュのみ・通信なし
python scripts/ws_eval_summary.py --report eval.json --basins-dir <同上> --obs-master <obs_master.json> \
    --profiles profiles.json --evidence-out evidence.json --evidence-md evidence.md
```

| 証拠 | 記録する値 |
|---|---|
| `reference` | 参考面積（川の防災情報）・算出面積・誤差 % |
| `coordinate` | `dams.json` の座標が観測所マスタの座標と同一か（`identical_to_station_master` / `differs_from_station_master` / `no_station_master`）とずれ量 m。**座標の正しさは判定しない** |
| `outlet_profile` | 半径 50/150/250/400/700/1000m の出口候補の上流面積・距離、採用出口から下流 3km の面積の増え方 |
| `method_agreement` | 貯水池法の面積と、河道法の候補面積の差 %（半径ごと）。河道スナップの基は対象外 |
| `lake` | 水面の面積と、集水域に対する比 %（**記録のみ**） |
| `basin_info` | 直接・間接流域の有無・値・出典・確認状態（`dam_basin_spec.csv`）・導水の判定 |

**評価区分（G1〜G4）**は、人手監査へ送る量を見積もるための分類。**公開可否・掲載可否には接続しない**。
区分の規則が使う数値は、既存の ±15%（参考面積との一致の目安。`watershed_qa` の面積誤差と同じ値）だけで、
新しい閾値は無い。水面比・座標のずれ・出口周辺のプロファイルは記録するだけで、区分の条件にしない。

| 区分 | 名称 | 規則 |
|---|---|---|
| G1 | official_verified | QA が PASS/WARN で、便覧の直接流域があり、導水の記載なし |
| G2 | official_with_diversion | 同上で、導水あり |
| G3 | reference_consistent | 便覧なし。参考面積と ±15% 以内で、QA が PASS/WARN |
| G4 | needs_evidence | QA が HOLD/FAIL/判定不能、または便覧なしで参考面積と乖離・参考面積なし |

**`dam_basin_spec.csv` の入口**（`dam_id` 単位）: `direct_km2` / `indirect_km2` / `total_km2`（分かっている値だけ）、
`source`（出典）、`basin_status`（`confirmed` / `unconfirmed`）、`note`。`unconfirmed` の行は数値を持てない
（推測値を入れさせない）。`confirmed` の行は数値（直接または合計）と出典が必須。行が無いダムは「未確認」として扱う。
検証は `build_basins.load_spec`。**この入口は受け皿であって、値の調査・入力はしていない。**

### 版の食い違いを起こさない

索引・ポリゴン・格子は別々のファイルなので、画面を開いたまま新しい版を公開すると
古い索引と新しい格子が組み合わさりうる。**同じ SW キャッシュ名や同じ dam_id は「同じ版」を保証しない。**

1. 各ファイルに**自分の内容ハッシュ**（sha256 先頭12桁）を `version` として書き込む
2. 索引が各部品の期待版を持つ（ダムごとの `v`、ポリゴンの `basins_version`）。索引が指す URL は
   `flow/<id>.json?v=<そのダムの版>`。索引が新しければ必ず新しい方を取りに行く
3. 取得した部品の版が索引の期待版と違えば**描かずに止めて**「再読み込みしてください」と出す（黙って混ぜない）
4. `docs/sw.js` で `/watershed/index.json` をネットワーク優先にした。
   Cache API の `match` は request の `cache: "no-cache"` を見ないので、キャッシュ優先のままだと
   索引だけが無期限に古くなる

### 方式

国土数値情報の流域界（W07 流域メッシュ）は使えなかった。富山県では収録が部分的で
（神通川水系は92km²分のみ）、単位も「単位流域」のためダムの集水域にならない。23基のうち7基は
ダム地点にメッシュ自体が無かった。

そこで**国土地理院の標高タイル**（`dem` = DEM10B、登録不要、地図タイルと同じ配信）から
地形解析で求めた。窪地埋め → D8流向 → 上流セル抽出 → 外周のポリゴン化 → 30m簡略化。
`scripts/build_basins.py`（単発実行、依存は numpy のみ）。

出力は `data/basins/`（**docs/ の外なので公開されない**）。GeoJSON 151.5KB / 23基 / 7,175頂点。
計算は全23基で約8分、標高タイル約1,000枚。

### 誤差は「合計」ではなく「直接流域」と比べる

**これが今回いちばん重要な発見。** 地形計算は導水（他の河川からの取水）を再現できないので、
ダム便覧の**直接流域面積**と比べるのが正しい。

| ダム | 便覧 合計 | 便覧 直接 | 便覧 間接 | 算出値 |
|---|---|---|---|---|
| 有峰ダム | 219.9 | 49.9 | **170.0** | 55.9 |
| 室牧ダム | 128.3 | 85.2 | **43.1** | 84.2 |
| 黒部ダム | 188.5 | 184.5 | **4.0** | 181.2 |

合計と比べると有峰は −77% の大外れに見えるが、直接流域と比べれば +11.9%。
**計算が正しいことと、導水判定が正しいことを同時に裏付けている。**

したがって表示では「**地形上の集水域**」と呼び、「流域面積」とは呼ばない。両者は別物。

### 精度（直接流域比）

| | 基数 |
|---|---|
| ±5%以内 | 16 |
| ±5〜15% | 3（和田川 −11.4%、有峰 +11.9%、白岩川 −6.5%） |
| **15%超** | **1（白岩川 +16.5%）→ 公開対象から除外**（境川・臼中は原因が判明して解消。白岩川は 2026-09-24 に河道起点へ切り替えて HOLD を解除） |
| ダム便覧に記載なし | 2（舟川・大谷。ただし川の防災情報の流域面積とは +2.0% / −1.3%） |

修正後の22基（公開候補。便覧の直接流域があるのは20基）の直接流域比は **最大 −5.4%（和田川）**。

### 原因の特定（2026-09-19）— 出口が貯水池の水面に乗っていた

境川 −38.7% と臼中 −37.6% は**同じ原因**だった。

集水域は本来「**貯水池に流れ込む範囲**」である。それを「堤体の近くで集水量が最大のセル1点に
流れ込む範囲」として求めていたため、その1点が**水面の上に乗った**ときに問題が起きる。
水面は平らなので、窪地埋め（Priority-Flood）が付けるごくわずかな傾きの向きで水面が分割され、
上流の一部しか拾えない。

**臼中で実証: 計算された集水域が、自分の貯水池の水面の 41.3% を含んでいなかった。**
ダムの集水域が自分の貯水池を含まないのは、定義上ありえない。

修正は `build_basins.py` の `find_reservoir()` と `upstream_of_set()`。
水面を見つけて**水面全体を起点**にする。見つからなければ従来のスナップ方式に落とす。

| ダム | 修正前 | 修正後 | 便覧（直接） | 誤差 |
|---|---|---|---|---|
| 境川 | 23.10 | **37.60** | 37.7 | **−0.3%**（← −38.7%） |
| 臼中 | 8.43 | **13.12** | 13.5 | **−2.8%**（← −37.6%） |
| 有峰 | 55.86 | **50.44** | 49.9 | **+1.1%**（← +11.9%） |

有峰にはもう一つ別の原因があった。河道選びの目安に便覧の**合計**（219.9＝導水込み）を
渡していたため、地形に存在しない 110km² 以上を探して候補が全滅し、最後に試した半径700m
（実距離677m）が採用されていた。**直接流域 49.9 で判定すれば半径150m・実距離174m**に収まる。

### 水面の取り方の点検（面積の一致だけで合格にしない）

`scripts/check_reservoirs.py` が、公式面積とは無関係な検査をして画像を書き出す。

**堤体で切ると水面が割れるか。** 貯水池は堤体でせき止められているので、堤体は水面の**端**にある。
端を切り落としても水面はひとつのまま残るはずで、2つに割れるのは水面が堤体をまたいで
下流の川までつながっている（＝別の水面を巻き込んでいる）しるし。

水面を検出した27基のうち、**割れたのは2基だけ**だった。この2基を公開対象から外している。

| ダム | 面積の一致 | 堤体で切ると | 判断 |
|---|---|---|---|
| **白岩川** | 22.43（−6.5%）→ 27.95（**+16.5%**）と悪化 | **2つに割れる** | 公開しない |
| **臼中** | 13.12（−2.8%）と良好 | **2つに割れる** | **面積が合っていても公開しない** |

そのほか、水面は次の性質を構造的に満たしている。

- **ひとつの連結成分**（8近傍）としてしか作らないので、離れた平地は入らない
- 標高は水位から ±1.5m の帯の中だけ（実測の標高幅 1.5〜3.0m）
- 堤体から 700m 以内に届いていること（届かなければ検出しない）
- 面積が 60km² を超えるものは水面とみなさない（平野・海よけ）
- 集水域が水面を **100% 含む**（含まなければ取りこぼし。全基で 100%）

### 明瞭な水面を検出できない場合

無理に補完せず、**従来のスナップ方式に落とす**。富山23基では11基がこれにあたる
（宇奈月・出し平・熊野川・刀利・五位・利賀川・子撫川・角川・上市川・上市川第二・朝日小川・舟川・大谷）。
落ちる条件は次のいずれか。

- 堤体から 700m 以内に「3×3の標高差が 0.6m 未満」のセルがない（水面が resolved されていない）
- その連結成分が 30セル未満（解像度に対して貯水池が小さい）

**解像度の選び方が効く。** 臼中は流域面積の目安に川の防災情報の 48.2km² を使うと z13（15.4m/セル）
になって水面を検出できず、便覧の 13.5km² なら z14（7.7m/セル）で検出できた。
目安には便覧の値を優先する。

データは `data/watershed/staged/held/` と `data/watershed/staged/index.local.json` に残してある（`.gitignore` 対象）。
原因が分かれば `EXCLUDED` から外して再生成するだけで公開対象に戻せる。

### 輪と雨を同じ解析結果から作る

以前は、描く輪（`build_basins` の細格子）と雨が降る範囲（`build_flowgrids` の粗格子）を
**別々に計算していた**ため、両者が食い違っていた（臼中 +59.9%、有峰 −9.2%）。
現在は `build_flowgrids` が細格子の集水域をそのまま粗格子へ間引いて雨の範囲にする。
粗格子の D8 は経路を描くためだけに使う。**輪と雨のずれ（面積）は公開候補22基で ±0.2% 以内。**（面積が合っていても位置がずれる可能性があるため、空間QAを別に行う。上記「パイプラインと品質ゲート」）

到着点は「点」ではなく**貯水池の水面**にした。粗い格子で1点だけを終点にすると、
水面のどこで止まるかが窪地埋めの微小な傾きで決まり、集水域の何割かが「出口へ届かない」
ことになる（境川で 36.2%）。実際にも雨は堤体の1点ではなく貯水池へ集まる。
**現在は届かない範囲が全基 1.6% 以内。**

### 導水のあるダムは「直接流域」と比べる

合計（直接＋間接）と比べると地形計算が外れているように見えるので、画面では分けて出す。

| ダム | 地形計算 | 便覧 直接 | 誤差 | 便覧 合計 | 導水で説明できる範囲 |
|---|---|---|---|---|---|
| 有峰 | 55.9 | 49.9 | **+11.9%** | 219.9 | 合計との差 −74.6% のうち **間接流域170.0km² は導水で説明できる**。残る +11.9% は導水では説明されない通常の計算誤差 |
| 室牧 | 84.2 | 85.2 | **−1.2%** | 128.3 | 同上（間接43.1km²）。残差はほぼ無い |
| 黒部 | 181.2 | 184.5 | −1.8% | 188.5 | 同上（間接4.0km²） |

**有峰だけは注意が要る。** 流出点のスナップ距離が 677m と全基で最大で、粗格子の集水域が
細格子ポリゴンより **−9.2%** ずれる（他の20基はいずれも ±1.6% 以内）。公開はするが、
この基だけ「輪」と「雨の範囲」の一致が他より緩い。

### 表示時に必ず書くこと（第2段階の要件）→ 実装済み

1. **全ダム共通**：「地理院の標高データから計算した概略です」をパネルとカードに常時表示 ✅
2. **導水のある基**（有峰・室牧・黒部）：`導水あり` のラベルと
   「この輪のほかに、別の谷からも水を引いています（間接流域 約○km²）。
   導水路の経路は公開資料で確認できないため描いていません」 ✅
3. **境川・臼中**：注記ではなく**公開対象から除外**した（上記）
4. **舟川・大谷**：`ダム便覧に記載なし` のラベルと
   「ダム便覧に該当の記載を確認できていないため、直接流域との比較はできていません。
   参考として川の防災情報の流域面積（約○km²）とは近い値になっています」 ✅
   — **記載が無いという事実**と、**幾何的には検証が通っていること**を分けて書く
5. 集水域（地形計算）／公式の流域面積（**直接**）／同（導水を含む合計）を並べて表示 ✅

分からないことを分からないと書く方針を、ここにも適用する。
**「流域面積」とは呼ばず「集水域（地形計算）」と書く**ことで、公式に確定した集水区域や
実際の水流観測と取り違えられないようにしている。

### 画面での体験（`docs/app.js` の `ws` モジュール）

| 操作 | 起きること |
|---|---|
| パネルの入口ボタン「この水は、どこから来る？」 | 集水域へ地図が寄り、尾根が描かれ、輪の内側に雨が降り、谷筋を流れてダムへ集まる |
| 雨を降らせている間に地図を押す | その地点に降った雨を1滴でたどる。届いたダムと道のり、下流の収録ダムを表示 |

貯水率・観測日時・貯水位・貯水量・流入量・水系/河川・詳細ページ導線・訪問記録・
共有リンク（`#basis=…&dam_id=…`、旧 `#dam=…`）の意味は変えていない。入口ボタンが1つ増えるだけ。ダムを切り替える・見つからない・候補一覧を出すときは、集水域の輪と雨を止める。

### 残り57基の準備状況（新規生成はしていない・配信もしない）

`scripts/build_basins.py` は `docs/data/dams.json` の全基を対象にするため、80基分の集水域ポリゴンが
`data/basins/` に生成された（富山以外の57基は**意図せず**生成されたもの。配信対象からは外してある）。
これは「全ダム対応」に向けた準備状況の材料になる。

| 区分 | 基数 | 内訳 |
|---|---|---|
| 自動処理で通りそう | **48** | 便覧の直接流域または川の防災情報と ±15% 以内 |
| 面積が合わない（個別判断） | **6** | 九頭竜 −38.6%（導水の可能性）／内村 −82.5%／小仁熊 −54.5%／小屋 −25.5%／豊丘 −20.9%／八ヶ川 −15.3% |
| 照合する面積が無い | **3** | 滝波・開谷・吉野瀬川（便覧にも川の防災情報にも記載なし） |

**「48基が通る」は面積の照合だけの話で、配信できる状態ではない。** 配信するには、富山と同じく
①水面の取り方の点検（堤体で切ると割れないか）②輪と雨の一致 ③到達率 を1基ずつ通す必要がある。
水面を検出した27基（富山9・他18）について堤体で切る検査は済んでおり、**富山以外の18基はすべて1つのまま**だった。

人手が必要になる条件は、富山23基から次の3つが分かっている。

1. **導水のあるダム** — 便覧の直接/間接の内訳が要る。合計しか無いと河道選びが飛ぶ（有峰）
2. **出典間で流域面積が食い違うダム** — 解像度の選択を誤り、水面を検出できなくなる（臼中）
3. **堤体が標高タイルで分解されないダム** — 水面が下流までつながる（白岩川）

### 実装中に直した3つの不具合（同じ罠を踏まないため）

1. **河道スナップの半径を固定にしていた** — 250m固定だと刀利ダムが−99.7%（河道に届かず1セル）、
   500mにすると角川ダムが+724%（隣の大きな川に飛ぶ）。小さい半径から試し、公式面積と桁が
   合った時点で採用する方式に変更。公式面積は「どの河道に乗せるか」の判定にのみ使い、
   結果の値には手を加えていない。
2. **範囲を広げて再計算するときスナップし直していた** — 格子を広げると流向場が変わり、
   スナップ先が別の川へ移る。**出口セルを緯度経度で固定**し、拡大後は同じ地点を使う。
3. **「面積が合っていれば拡大しない」ガードを入れたら逆効果だった** — 宇奈月ダムなど
   大流域で必要な拡大まで止まり −12.5% になった。2 の修正で不要になったため撤去。

## 訪れたダムを地図に残す

ダムの詳細パネルから **「現地で訪問を記録する」**。現在地がそのダムの近くなら、
その場で訪問として記録され、地図のピンに色が残る。

### 見え方

| | |
|---|---|
| **1基も訪れていないとき** | これまでどおり。全部のピンが色つき。何も伏せない |
| **1基でも訪れると** | 訪れた場所は色を保ち、外周の縁が琥珀色に変わる。まだの場所は静かに色が引く |
| **記録した瞬間** | そのピンだけ、色が戻りながら一度だけふわりと光る |

貯水率のリング・数字・「—」の出し方は、**訪問の有無で一切変わらない**。
色分けが合わない人は、凡例の下の「訪れた場所に色を残す」で止められる。

### 判定のしかた

ダムの座標は堤体を指すので、「堤体の一点に立たないと記録できない」設計にはしない。
現地では危険で不便になるため。

```
許容距離 = 600m + min(GPSの誤差, 300m)      最大 900m
```

判定は常に **最も近い1基だけ**。最も近い2基（上市川 / 上市川第二）でも 1,944m
離れているので、最大 900m まで広げても取り違えは起きない。
別のダムの近くにいる場合は「いまは◯◯ダムの近くにいるようです」と案内する。

### 残るもの

`localStorage` の `damtabi.visits.v1` に、**この端末の中だけ**。
サーバへは何も送らない。位置情報そのものは保存しない（距離と誤差だけ残す）。

- 訪問日
- 訪れた日にダム旅で見えていた観測値と、**その観測日時**

観測値は「訪問した瞬間の貯水率」ではない。画面に出ていた値なので、
必ず観測日時とセットで「訪れた日にダム旅で見えていた値」と書く。

### 座標に注意が要るダム

**舟川ダム**は公的資料の間で座標が約4.5km食い違っている（→「舟川ダムの座標について」）。
ダム旅が採る座標は川の防災情報・国土数値情報と同値だが、現地で記録できるかは未検証。
座標は推測で直さない。

## 行ったら、こんなのもあります（観光情報）

ダムの詳細（地図のパネルと個別ページの両方）に、そのダムだからこそある寄り道を出す。
「行ってみようかな」と「実際に訪れた」の間を埋めるための欄。

貯水率 → ダムの基本情報 → **見どころ** → 訪問の記録、の順に並ぶ。
既存の表示は何も減らしていない。データが無いダムでは欄ごと出ない。

### 扱ってよいもの

**そのダムだからこそ存在する、またはダムとの関わりが強いもの**だけ。
ダムカード、ダムカレー、展示館、見学、ダムの売店など。
普通のホテル・温泉・一般の飲食店は入れない（観光ポータルにはしない）。

### 書いてよいもの

- 公式が出している**事実**（配布時間、実施期間、予約の要否など）
- **ダム旅が自分で書いた**短い説明

他所の紹介文をそのまま写さない。店舗・施設・商品の画像やロゴは使わない。
写真は無くてよい。確認できない価格・営業時間は書かない。

### データ

`docs/data/spots.json`。ダムID をキーに配列で持つ。

```json
{ "dams": { "toyama-kurobe": [
  { "kind": "eat",             // collect 集める / eat 食べる / see 見る / buy 買う
    "title": "黒部ダムカレー",
    "summary": "ダム旅が書く1〜2文",
    "facts": [{ "label": "場所", "value": "黒部ダムレストハウス" }],
    "note": "現地判断に効く注意（季節・予約・在庫など）",
    "source": "https://...",           // 一次情報のURL
    "source_name": "誰が出している情報か",
    "checked": "2026-09-07" }          // いつ確認したか
]}}
```

**`source` と `checked` は必ずセットで持つ。** 時間・期間・料金は変わるので、
「誰の、いつの情報か」が落ちると事実でなくなる。画面にも常に出す。

## 旅の記録のバックアップ／復元

GPS訪問記録は端末の `localStorage` にしかない。機種変更・ブラウザ変更・
データ消去で消えうるため、**自分でファイルに保存し、あとで自分で戻せる**
仕組みを足した。アカウントもサーバーも使わない。

「旅の記録」の一覧（`#trip`）の下に2つのボタンがある。

- **旅の記録を保存** — 今の記録を `damtabi-trip-backup-YYYY-MM-DD.json` として
  ダウンロードする。訪問記録が0件でも押せる（空の状態で保存される）
- **保存した記録を読み込む** — 選んだファイルを検証し、今の記録に**安全に**合わせる

### バックアップに入るもの・入らないもの

| 入る | 入らない |
|---|---|
| どのダムを訪れたか（ダムID） | GPSの緯度・経度 |
| 訪問日 | 距離・GPS精度（`distance_m` / `accuracy_m`） |
| その日ダム旅で見えていた貯水情報と観測日時 | 端末情報、その他の識別子 |

```json
{
  "app": "damtabi",
  "kind": "trip-backup",
  "schema_version": 1,
  "generated_at": "2026-09-07T12:00:00.000Z",
  "region": "toyama",
  "visits": [
    { "dam_id": "toyama-kurobe", "visited_at": "2026-09-07T09:00:00.000Z",
      "seen": { "obs_time": "2026/09/07 09:50", "data_status": "ok",
                "rate_irrigation": {"value": 85.2, "status": "ok", "reason": null},
                "rate_effective": {"value": 19.6, "status": "ok", "reason": null},
                "storage_level_m": {"value": 240.78, "status": "ok", "reason": null} } }
  ]
}
```

`schema_version` は中身の意味を表す番号（画面の見た目とは無関係）。今後
石川県対応やダムカード記録などが増えても、この番号だけを見て
「読める／読めない」を判断できるようにしてある。

### 復元の安全策

読み込み前に必ず検証し、**1つでも致命的な問題があれば今の記録には一切触れない**。

- JSONとして壊れている → 拒否
- `app`/`kind` がダム旅の形式でない（無関係なJSON） → 拒否
- `schema_version` が読めない、またはこのページより新しい → 拒否
  （「新しいダム旅で保存された記録のようです」と表示。ページを更新すれば直る想定）
- 1件も有効な記録として読めない → 拒否
- ダムIDが `__proto__` 等、内部の仕組みに触れる名前 → その項目だけ無視
  （オブジェクトへの代入で汚染が起きないよう、既知の禁止名をはじく）

個々の項目は、訪問日が読めないものだけ**その項目に限って**読み飛ばす
（ファイル全体は拒否しない。1件でも壊れていたら全部やめる、という
過剰な安全策は「ほぼ良いファイルなのに丸ごと復元できない」を生むため）。

### 既存記録との統合

単純な上書きはしない。**ダムを失わないこと**を最優先にした、単一の機械的なルール：

- そのダムの記録が無ければ **追加**
- 両方にあれば、**より古い訪問日（＝最初に行った日）を残す**

これなら常に安全（最悪でも「重複した記録の日付が数日ずれる」以上のことは
起きない）ので、統合のたびに選択肢を出す必要がない。ただし、記録がすでに
1件でもある状態で読み込むときは、実行前に一言だけ確認する
（「今の旅の記録に、保存しておいたファイルの記録を合わせます。
すでにある記録が消えることはありません。よろしいですか？」）。
記録が0件のとき（失うものが無いとき）は確認なしでそのまま読み込む。

復元後は「読み込んだ記録：3基分／新しく増えた記録：1基／
すでに記録済みだった：1基／今の記録：3基 → 4基」のように、
何が起きたかを数字で示す。

## 独自ドメインへの移行

**2026-09-06 に `damtabi.com`（Cloudflare Registrar で取得）へ移行済み。**
以下は実施した手順で、別ドメインへ移す場合もそのまま使えます。

公開URLは `https://damtabi.com`。旧URL `https://hikaclaude.github.io/damtabi/` は
GitHub Pages が自動で 301 リダイレクトします。

### 手順

**1. ドメインを取得し、DNS を設定する**

apex ドメイン（`damtabi.com`）で公開する場合、DNS に GitHub Pages の A / AAAA レコードを設定します。

```
A     @   185.199.108.153
A     @   185.199.109.153
A     @   185.199.110.153
A     @   185.199.111.153
AAAA  @   2606:50c0:8000::153
AAAA  @   2606:50c0:8001::153
AAAA  @   2606:50c0:8002::153
AAAA  @   2606:50c0:8003::153
```

`www.damtabi.com` を使う場合は CNAME を `hikaclaude.github.io.` に向けます。
（上記IPは GitHub の公式ドキュメントで最新を確認してください。変わることがあります）

**2. `site.json` の `base_url` を書き換える** ← コード側の変更はここ 1 行だけ

```json
{ "base_url": "https://damtabi.com", ... }
```

末尾スラッシュは付けません。サブディレクトリが無くなる点に注意
（`https://hikaclaude.github.io/damtabi` → `https://damtabi.com`）。

**3. CNAME ファイルを置く**

GitHub Pages はリポジトリ内の `CNAME` ファイルで独自ドメインを認識します。
公開ディレクトリが `docs/` なので、置き場所は **`docs/CNAME`** です。

```bash
echo "damtabi.com" > docs/CNAME
```

改行以外は入れず、1行だけ。**サブドメインを含む完全なホスト名**を書きます（`https://` は不要）。

> **注意**: GitHub の Settings → Pages 画面で独自ドメインを設定すると、GitHub が
> `docs/CNAME` を**自動でコミットします**。手で作った場合と二重にならないよう、
> どちらか一方（画面設定 or ファイル）に統一してください。おすすめは
> **先に `docs/CNAME` をコミットしてから Settings で確認する**順です。
>
> また `CNAME` は `build_site.py` が触りません。再ビルドで消えることはありません。

**4. 再ビルドして push**

```bash
python scripts/build_site.py   # canonical / og:url / og:image / sitemap / robots / manifest が追随
git add -A && git commit -m "chore: 独自ドメインへ移行" && git push
```

**5. HTTPS を有効にする**

Settings → Pages → **Enforce HTTPS** にチェック。証明書の発行に数分〜1時間かかります。
チェックできない間は DNS の伝播待ちです。

**6. 確認**

```bash
curl -sI https://damtabi.com/ | head -1
curl -s https://damtabi.com/ | grep -o '<link rel="canonical"[^>]*>'
curl -s https://damtabi.com/robots.txt
```

canonical と sitemap が新ドメインになっていること、`/dam/toyama/unazuki/` が開くことを確認します。

### 旧URLからどうつなぐか

**GitHub Pages が自動でリダイレクトします。** 独自ドメインを設定すると、
`https://hikaclaude.github.io/damtabi/...` へのアクセスは
対応するパスの `https://damtabi.com/...` へ **301 リダイレクト**されます。
パス構造は変えないので、`/dam/toyama/unazuki/` のような個別ページもそのまま引き継がれます。

**したがって、リダイレクト用のファイルを自分で用意する必要はありません。**
このために URL 設計を `/dam/{都道府県}/{読み}/` で固定してあります。

移行後にやること:

1. **Search Console に新ドメインのプロパティを追加**し、`https://damtabi.com/sitemap.xml` を送信
2. 旧プロパティ（`hikaclaude.github.io/damtabi`）は消さずに残す。301 が認識され、
   評価が新ドメインへ引き継がれるまで数週間かかります
3. **OGP のキャッシュを更新**。SNS は URL 単位で画像をキャッシュするので、
   各プラットフォームのデバッガで新URLを再取得させます
4. 告知済みのリンクがあれば新URLに差し替える（301 が効くので急ぎではありません）

### やってはいけないこと

- **`base_url` を変えずにドメインだけ切り替える**。canonical が旧URLのまま残り、
  検索エンジンは「新URLは旧URLの複製」と判断します。必ず `site.json` → 再ビルド → push の順で。
- **`docs/CNAME` を消す**。消すと独自ドメインが解除され、リダイレクトも止まります。
- **URL 構造を同時に変える**。ドメイン移行とパス変更を一度にやると、
  何が原因で順位が落ちたか分からなくなります。分けて行ってください。

### アクセス把握と Cloudflare（訂正あり）

GitHub Pages は**アクセスログを提供しない**。いま利用状況を知る手段は
Google Search Console（＝Google検索経由の表示回数とクリック数）だけである。

サイトに計測コードを置けば全アクセスを数えられるが、**利用者の端末から外部へ
リクエストを出す**ことになり、「追跡しない」という方針と合わないため採用していない。
GoatCounter も同じ理由で見送った。

**訂正：Cloudflare Web Analytics は方針に合わない。**
移行前のメモに「Cloudflare 経由なら計測コード不要」と書いていたが、これは不正確だった。
Cloudflare には名前の似た別物が 2 つあり、性質がまったく違う。

| 機能 | 仕組み | 方針との整合 |
|---|---|---|
| **Web Analytics** | `static.cloudflareinsights.com/beacon.min.js` を読み込む **JavaScript ビーコン方式**。Cookie は使わないが、**利用者の端末から外部へリクエストが出る** | **合わない。使わない** |
| **Analytics & Logs（トラフィック分析）** | プロキシ経由の全リクエストを**エッジで集計**。JavaScript も Cookie も不要で、利用者の端末には何も追加されない | 合う |

Web Analytics には特に注意すべき点がある。プロキシ経由のドメインで有効化すると、
Cloudflare が**エッジで HTML に script タグを自動注入する**。リポジトリのファイルは
一切変わらないのに、利用者に届く HTML にはビーコンが入っている状態になる。
気づきにくい形で方針が破られるので、**有効化しない**。

方針に合うのは Analytics & Logs のほうだけ。使うには DNS レコードを
プロキシ（オレンジの雲）に切り替える必要があり、手順は次のとおり。

1. ドメイン移行を完結させる（Enforce HTTPS まで。**済**）
2. Cloudflare の SSL/TLS 暗号化モードを **Full (strict)** にする
3. DNS レコードをオレンジ（プロキシ）に切り替える
4. Analytics & Logs でトラフィックを見る
5. **Web Analytics は有効化しない**

証明書の発行前にプロキシを有効にすると Let's Encrypt の検証が失敗するため、
**順序を入れ替えないこと**。

### Organization へ移す場合（将来の選択肢）

`damtabi-lab` のような Organization に移管する場合も、**独自ドメインを先に当てておけば
公開URLは変わりません**（`https://damtabi.com` のまま）。
リポジトリ移管時に GitHub Pages の設定と `docs/CNAME` を再確認するだけで済みます。
**独自ドメインを先に取る方が、後の移管が楽になります。**

  "base_obs_time": "2026/09/04 20:30",
  "source": { "name": "国土交通省 川の防災情報", "...": "..." },

    {

値は必ず `{value, status, reason}` の 3 点セットです。`value` が入るのは `status === "ok"` のときだけ。

## バッチの挙動

- 出力は毎回まっさらに作り直します。**前回の JSON は読みません**（値の使い回しを構造的に不可能にするため）。
- 最新スロットが未生成のときは 10 分ずつ最大 6 回遡って探します。
- HTTP エラーは 3 回までリトライ（404 は即中断）。すべて失敗したら `fetch_failed` として理由付きで記録し、
  **他のダムの処理は続行**します。1 基の失敗で全体を落としません。
- リクエスト間に 0.3 秒空けています（1 回の実行で約 50 リクエスト）。
- マスタが取れなくても実測値の取得は続行します（洪水期の注記が出ないだけ）。

```
[fetch_dams] 基準観測時刻 2026/09/04 20:30
  宇奈月ダム     利水=87.6%      有効=20.2%      [ok] 2026/09/04 20:30
  熊野川ダム     利水=—(missing) 有効=—(missing) [missing] 2026/09/04 20:20
  刀利ダム      利水=—(not_provided) 有効=—(not_provided) [not_provided] 2026/09/04 20:20
  黒部ダム      利水=—          有効=—          [no_source]
[fetch_dams] 内訳 {'ok': 15, 'missing': 2, 'not_provided': 3, 'no_source': 3}
```

## 複数県対応（富山県・石川県、2026-09）

ダム旅は当初「富山県専用」に近い作りでしたが、石川県を2県目として足すタイミングで、
3県目以降も同じ手順で増やせる構造に直しました。

### 県を1つ足すのに必要な作業

```
1. prefs/prefectures.json に1行足す（key / name / rate_source）
2. prefs/<県>/dams.csv（現在値あり）か dams_nodata.csv（現在値なし）を置く
3. dam_slugs.csv に <ダム名,県key,slug> を足す
4. python scripts/fetch_dams.py && python scripts/build_site.py
```

地図の初期表示範囲・一覧の県区切り・sitemap・OGPの県名・構造化データの
`addressRegion` は、すべて `prefs/prefectures.json` と各ダムの `pref` から
自動で決まる。県ごとにコードを書き足す必要はない。

イラスト（カード・地図ピン）は `docs/img/dams/<ダムID>.webp` /
`docs/img/dam-icons/<ダムID>.webp` を置いて `python scripts/register_images.py`
を実行すれば登録される。置いていない間は「イラスト準備中」のまま自然に表示される。

### 収録対象の考え方（コア＋例外）

ダムを収録するかどうかは、2段構えで判断する。

- **コア**：公的に完成・管理中と確認でき、公式のダム管理一覧または
  川の防災情報等で確認でき、名称・所在地・座標・水系・河川・管理者を
  公的一次情報で確認できるもの。機械的に判定できる。
- **例外**：コアの条件を満たさなくても、ダム旅として掲載する価値が高いと
  人が判断して足すもの。黒部・有峰・出し平（発電専用で現在値の公開が無いが、
  著名な観光地）がこれにあたる。

各ダムのレコードに `inclusion`（`core` / `exception`）と、例外の場合は
`inclusion_reason`（なぜ足したか）を持たせてある。`dams.json` に出力される
ので、後から「なぜこのダムが載っているか」を追える。

### 石川県 12 基

石川県河川課「石川のダム」が完成・管理中として掲載する12基と、
国土交通省 川の防災情報のダムカード配布情報に載る石川県の12基が完全一致したため、
この12基を初期版の収録対象とした（全基コア）。

現在値（貯水率）は、ダム旅が使える公開の取得元をまだ確認できていない。
`prefs/prefectures.json` の `rate_source` を `"none"` にしてあり、
取得バッチはこの県には取りに行かない。推測で埋めることはしていない。
一覧・地図とも「現在値未確認」の県として自然に表示され、アプリは壊れない。

石川県の座標・水系・河川は、県公式サイト「石川のダム」の各ダム詳細ページ
（水系名・河川名・所在地の記載と、ページに埋め込まれた Google マップリンク）
を一次情報として採用した。**ダム便覧（第三者サイト）は当たりを付ける手がかり
としてのみ使い、採用した値の根拠にはしていない。**

例外が1件ある。新内川ダムは、石川県公式ページのマップリンクが犀川ダムと
経度まで完全に一致しており、県サイト側の入力誤りと判断した。この1基だけ、
国土交通省 川の防災情報の該当観測所ページが示す座標を採用している
（`prefs/ishikawa/dams_nodata.csv` の該当行に理由を記載）。

### 3県目を追加するときの作業量

上の4手順がそのまま使える。今回の石川県対応で増えた「県ごとの分岐」は
`fetch_dams.py` 側に無く（登録簿を回すだけ）、`build_site.py` 側も
一覧の県見出しと構造化データの `addressRegion` が自動で追随する。
残る作業は実質、**その県のダムを調べてCSVを書くこと**だけになる。

### GPS訪問判定と地図表示座標の分離について

現在、地図に置く位置と GPS 訪問判定の基準地点は、どちらも `dam.lat` /
`dam.lon` という同じ1組の値を使っている。これは意図した割り切りで、
「地図表示用の代表点」と「安全に立ち寄れる現地判定点」を分けたいダムが
出てきたときは、CSV に列を1つ足し（例: `visit_lat` / `visit_lon`）、
`app.js` の GPS 判定側だけそちらを優先して読む2行程度の変更で対応できる。
未設定なら今までどおり `lat` / `lon` にフォールバックするので、
既存データも既存コードも壊さずに導入できる。今回この分離は行っていない。
