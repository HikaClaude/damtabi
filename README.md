# ダム旅 / DAM TABI

**旅の寄り道に、ダムはいかが？**

ダムを地図から探して、知って、実際に見に行くためのアプリです。当面は富山県の23基が対象。

バッチ（Python）が国土交通省「川の防災情報」から貯水状況を取得して `docs/data/dams.json` に
書き出し、SPA（MapLibre GL JS ＋ 地理院タイル）がそれを読んで表示します。サーバレスの静的サイトです。

| | |
|---|---|
| アプリ名 | ダム旅（DAM TABI） |
| 制作名義 | DAM TABI LAB |
| 公開URL | https://hikaclaude.github.io/damtabi/ |
| 対象 | 富山県の23基（将来的に全国へ拡張予定） |

> **名称について**：「ダム旅」は一般的な表現でもあります。名称の独占性ではなく
> 「見ただけで意味が伝わること」を優先して採用しました。サービスとしての固有性は
> ダム旅 / DAM TABI・DAM TABI LAB・ロゴ・アイコン・オリジナルのダムイラスト・UI の
> 組み合わせで作っていきます。

## いちばん大事な原則

> **取れなかったデータは「取れなかった」と表示する。**

推定値で埋めない。前回値を使い回さない。片方の貯水率でもう片方を代用しない。
値が無いときは `—` を出し、**なぜ無いのか**を必ず添えます。

理由は 5 種類に分けています。

| status | 表示 | 意味 | 今日の該当 |
|---|---|---|---|
| `ok` | 数値 | 取得できた | 15 基 |
| `missing` | — 欠測 | 観測所からデータが届いていない | 熊野川・朝日小川 |
| `not_provided` | — 未提供 | その観測所ではその項目を公表していない | 刀利・五位・臼中 |
| `closed` | — 閉局 | 観測を行っていない | （現在なし） |
| `fetch_failed` | — 取得失敗 | 通信・サーバ側の問題で取れなかった | （現在なし） |
| `no_source` | — データ提供なし | そもそも公開している事業者がいない | 黒部・有峰・出し平 |

判定はダム単位ではなく**項目単位**です。たとえば熊野川ダムは貯水位（313.14 m）は取得できて
貯水量・貯水率だけが欠測なので、貯水位は数値を出し、貯水率だけ「— 欠測」と出します。

## 運用方針：更新は手動で行う

**このアプリは自動更新しません。更新は人が手で実行します。これが正規の運用です。**

川の防災情報の[取り扱い上の注意](https://www.river.go.jp/kawabou/kwb_apend/html/caution.html) 1.2) に、
ツール等による**定期的な**データ収集は控えるよう明記されているためです（詳細は次節）。
定期実行（cron）は意図的に無効にしてあり、人が判断して実行する形にしています。

### 更新のしかた

```bash
# 1) 貯水率を取得して docs/data/dams.json を作り直す
python scripts/fetch_dams.py

# 2) ダムごとの静的ページ・sitemap・manifest を作り直す
python scripts/build_site.py

# 3) 公開（GitHub Pages なら push するだけ）
git add docs/data/dams.json docs/dam docs/index.html docs/sitemap.xml docs/robots.txt docs/manifest.json
git commit -m "data: 貯水率を更新"
git push
```

GitHub 上で実行したい場合は、Actions タブから `fetch-dams` ワークフローを
**Run workflow** で手動起動しても同じことができます（cron は無効のままです）。

### 更新のタイミングの目安

| 状況 | 目安 |
|---|---|
| 通常時 | **週1〜2回**。渇水期・出水期は多めに |
| 渇水のニュースが出たとき | その都度 |
| 大雨・台風の前後 | 更新するより、利用者を[川の防災情報](https://www.river.go.jp/kawabou/pcfull/tm)へ誘導するのが適切 |
| イラストを追加したとき | `make_images.py` も実行（貯水率の取得は不要） |

**防災用途はこのアプリの守備範囲ではありません。** 出水時のリアルタイム性が要る場面では
川の防災情報を見てもらう前提で、各ダムのページに公式ページへのリンクを置いてあります。

1回の実行で相手サーバに出すリクエストは **約21件**です（観測所マスタはローカルにキャッシュ済み）。

### 貯水率が取れなくても壊れない

手動運用では更新が数日空きます。そのため「いつの値か」の見せ方を作り込んであります
（→「古い値を現在値に見せないための仕組み」）。
また、全基が取得不可になってもアプリは成立します（`data_status` の `no_source` 扱い）。

## ⚠ データ取得の利用条件

**現在の取得方式は、川の防災情報の利用条件上「お控えください」と明記された行為に該当します。**
上記のとおり**定期実行をやめて手動運用にする**ことで当面の折り合いをつけていますが、
FRICS への照会結果によっては経路の変更が必要になります。

### 何が書かれているか

[取り扱い上の注意](https://www.river.go.jp/kawabou/kwb_apend/html/caution.html) の 1.2)（原文）:

> 当ホームページは一般の方々が通常のブラウザで閲覧されることを前提に情報を掲載しています。
> **ツール等による定期的なデータ収集は、サーバに過度の負担がかかりサービス提供に支障をきたすため、
> お控えいただきますようお願いいたします。**
> 商用・非商用を問わず、定期的・定常的なデータ収集を行われる場合は、以下に記載するリンク先ページより
> データ配信を受けることができますのでご利用ください。
> ・河川情報数値データ配信事業 https://www.river.or.jp/koeki/opendata/index.html
> なお、一定期間の通信量が著しく多い場合や高頻度のアクセスが確認された場合、
> 利用元に対してアクセス制限を行う場合があります。

姉妹サイトの[水文水質データベース](http://www1.river.go.jp/caution.html)にも同趣旨の記載があります
（「ツール等による、自動的なデータ収集等は…原則としてご遠慮ください」）。
**無料で自動取得してよい公式経路は見つかりませんでした。**

問題になっているのは「定期的・定常的」であることなので、
**cron を止めて人が都度実行する形にし、リクエスト数も削減**しています。
これで完全に白と言い切れるわけではありません。判断の分かれ目なので、FRICS へ照会中です。

### データそのものの利用は問題ない

取り扱い上の注意 2. は明確です。

- コンテンツは**複製・公衆送信・翻案等が自由**、**商用利用も可**
- **数値データは著作権の対象ではない**ため、そもそも本ルールの適用外で自由に利用できる
- 政府標準利用規約（第2.0版）準拠、**CC BY 4.0 と互換**
- 出典の記載が必要。記載例は「出典：国土交通省　川の防災情報ホームページ（当該ページのURL）」、
  加工した場合は「国土交通省　川の防災情報ホームページ（URL）を加工して作成」

→ **問題は「データを使うこと」ではなく「自動で定期的に取りに行くこと」だけ**です。

### 正式な代替手段と費用（照会中）

**水防災オープンデータ提供サービス（河川情報数値データ配信事業）** — 一般財団法人河川情報センター
（FRICS）が国交省の事業として配信。テレメータ「ダム諸量」に貯水位・貯水量等が含まれます。

| 項目 | 単位 | 月額（税抜） |
|---|---|---|
| ダム諸量（国所管） | 地方整備局ごと | 2,100円 |
| ダム諸量（都道府県所管） | 都道府県ごと | 2,100円 |
| 通信回線負担金（インターネット回線） | 一式 | 9,600円 |

- **富山県だけの場合**：北陸地整 + 富山県 + 回線 = **月 13,800円（税抜）／年 約18万円**
- **全国に広げた場合**：10地整 + 47都道府県 + 回線 = **月 約129,300円（税抜）／年 約155万円**
- **プッシュ型の配信**なので受信側にサーバが要り、現在のサーバレス構成が崩れます。
- 申込書・契約が必要（問い合わせ: haisin-info@river.or.jp）

照会内容の案：「非商用の観光情報アプリ「ダム旅」。富山県内20観測所、更新は手動で週1〜2回、
1回あたり約21リクエスト。この程度でも配信契約が必要か、Web取得が許容される条件があるか」。

### 参考: 他の経路

- **ダム諸量データベース**（[mudam.nilim.go.jp](https://mudam.nilim.go.jp/home)、国総研）
  国・水機構・都道府県のダムの**統計値**を公開。平成5年以降。ただし
  **貯水率は項目に無く**（貯水位・流入量・放流量・水温・濁度・水質）、リアルタイムでもないため
  現在値には使えません。ただし**平年値の算出には有力**なので、閾値設計を見直すときの候補です。
- **富山県の公表**：土木部所管16ダムの貯水率は報道発表PDFで不定期に出るのみ。機械可読な定期配信なし。
- **富山防災WEB**：貯水位のみ。貯水率・貯水量なし（16基）。

## 使い方

更新の手順は「運用方針」に書いたとおりです。ここでは補足だけ。

```bash
# ローカルで表示（file:// では fetch できないので簡易サーバを使う）
cd docs && python -m http.server 8765
# → http://127.0.0.1:8765/
```

`docs/` をそのまま GitHub Pages / Netlify / S3 などに置けば動きます。ビルド不要、API サーバ不要。

### 公開URLの設定は `site.json` の 1 行だけ

```json
{ "base_url": "https://your-domain.example/dam-map", ... }
```

ここを書き換えて `build_site.py` を実行すれば、
**canonical / og:url / og:image / sitemap.xml / robots.txt / manifest.json / 地図画面のメタ**が
すべて追随します。独自ドメインへの移行もこの 1 行です。

地図画面（`docs/index.html`）は手書きの HTML ですが、URL に依存するメタだけは
`<!-- BEGIN generated-site-meta -->` 〜 `<!-- END generated-site-meta -->` で囲ってあり、
その中身を `build_site.py` が生成します。二重管理になりません。
（`--base-url` 引数と環境変数 `SITE_BASE_URL` でも一時的に上書きできます。）

アイコンと OGP 画像は**単発**スクリプトで作ります（毎回の更新では不要）。

```bash
python scripts/make_images.py          # アイコン + 全ダムのOGP画像
python scripts/make_images.py --icons-only
```

ローカルの Chrome / Edge のヘッドレスでラスタライズします（画像ライブラリ不要）。
生成物は日々変わる数値を含まないので、そのままコミットして使い回せます。

`.github/workflows/fetch-dams.yml` は**手動起動（workflow_dispatch）専用**にしてあります。
cron はコメントアウトしてあり、理由もファイル内に書いてあります。

### URL で状態を共有できる

- `#dam=宇奈月ダム` … そのダムの詳細を開いた状態で開く
- `#basis=effective` … 有効貯水率で色分けした状態で開く

## 出典表記

画面上に**常時表示**しています（地図画面はヘッダ内の 1 行、各ページはフッタ）。

> 出典：国土交通省　川の防災情報ホームページ を加工して作成 ／ 地図：地理院タイル（国土地理院）

- **国土交通省**：[取り扱い上の注意](https://www.river.go.jp/kawabou/kwb_apend/html/caution.html) 2.1)
  の記載例どおりの文言にしています。数値を JSON に再構成しているので、同 2.1)イ に従い
  「加工して作成」も明示しています（リンク先が「当該ページのURL」に当たります）。
- **国土地理院**：地理院タイルは「国土地理院」または「地理院タイル」と記載し、
  [地理院タイル一覧ページ](https://maps.gsi.go.jp/development/ichiran.html)へのリンクを付けることが
  求められています。両方満たしています。ウェブサイトからのリアルタイム読み込みは申請不要です。

地図画面では MapLibre 内蔵の attribution コントロールを CSS で隠し、自前の表示に置き換えています。
出典をヘッダの中に置いたのは、**詳細パネルにも凡例にも決して隠されない場所がそこだけ**だからです
（地図の右下に置くと、詳細パネルを開いたときに覆われてしまう）。

内蔵の attribution コントロール自体は削除せず CSS で隠すだけにしています。
`attributionControl: false` を指定すると MapLibre GL JS 4.7.1 では `load` イベントが発火せず、
地図が描画されなくなるためです（実測して確認）。

なお地図のピンは `load` を待たずに配置しています。ピンは DOM オーバーレイなので
スタイルの読み込みを待つ必要がなく、**タイルが出ない状況（オフライン・タイル配信の不調）でも
ダムの位置と貯水率は読める**ようにするためです。

## 発見性（SEO / SNS / PWA）

### ダムごとの静的ページ

`/dam/{slug}/` にダム 1 基 = 1 枚の HTML を生成します。**値はサーバ側（バッチ）で埋め込み済み**で、
JavaScript なしでも本文が読めます。

- `title` と `meta description` はダムごとに個別。ダム名・所在地・水系・その日の貯水率を含みます
- `canonical` / OGP / Twitter Card / JSON-LD（`Place` と `BreadcrumbList`）を各ページに付与
- `sitemap.xml`（全 25 URL）と `robots.txt` を自動生成
- 地図のピンをタップ → 詳細パネルの「◯◯ダムの詳細ページ →」から遷移
- ヘッダの「ダム一覧」から `/dam/` の一覧ページへ。一覧から各ページへ内部リンク
- 各ページから「地図でこのダムの位置を見る →」で `#dam=◯◯` 付きの地図へ戻る

### URL 設計（全国化しても壊れないように）

URL は **`/dam/{都道府県}/{読みのローマ字}/`** です（`/dam/toyama/unazuki/`、`/dam/toyama/kadokawa/`）。
数値の観測所コードではなく読みにしたのは、検索結果や SNS で意味が読み取れるほうが発見性に効くためです。

**都道府県を挟んでいるのは、全国化したときの同名衝突を今のうちに避けるため**です。
ダム名の重複は例外ではなく前提で、たとえば大谷ダムは富山県のほかに新潟県にもあります。
県セグメントが無いと全国化の時点で URL の作り直しが要りますが、それは
「すでに検索エンジンに拾われた URL を壊す」というSEO上いちばん高くつく作業です。
市町村ではなく都道府県にしたのは、市町村合併では変わるが都道府県は実質変わらないためです。

安定キーの持ち方は次のとおりです。

- `dam_slugs.csv`（`dam_name, pref, slug`）が**唯一の対応表**で、リポジトリ内で手管理します。
  データ源の仕様が変わっても、ここを触らない限り URL は変わりません。
- `dams.json` の `id` は `toyama-unazuki` の形。**取得元の観測所コードに依存しない自前のキー**で、
  イラストの割り当て（`illustrations.json`）と OGP 画像のファイル名にも同じ id を使います。
- 取得元固有のコード（13桁の `obsFcd`）は `obs_fcd` / `source` に分けて持っています。
  川の防災情報をやめても、URL とイラストの紐付けは影響を受けません。

読みは川の防災情報のマスタ（`obsKana`）で確認済みです（角川ダム＝かどかわ、舟川ダム＝ふながわ など）。

### OGP

- トップと一覧：`docs/img/og/site.png`
- 各ダムページ：`docs/img/og/{id}.png`（ダム名・水系・所在地入りの 1200×630）

OGP 画像には**日々変わる数値を入れていません**。SNS 側は画像を長期キャッシュするので、
古い数値が貼り付いたまま残るのを避けるためです。数値は `og:description` に入れて毎日更新します。

**イラストができたら OGP は自動で差し替わります。** ダムごとに OGP を手作りする必要はありません。

1. 3:2 のイラストを `docs/img/dams/` に置く
2. `docs/data/illustrations.json` にダムID（`toyama-unazuki` 等）で登録する
3. `python scripts/make_images.py` を実行する

`make_images.py` が 3:2 のイラストを 1200×630 に `object-fit: cover` で切り出し、
下部にグラデーションを重ねてダム名・水系・所在地を載せた OGP 画像を作ります。
同じ `illustrations.json` を地図の詳細パネルとダムページも見ているので、
**登録は1箇所だけ**で地図・静的ページ・OGP の3か所に反映されます。

### Google Search Console

アクセス把握は **Search Console だけ**にしている。サイトに計測コードを置かないので、
利用者の端末から外部へ余計なリクエストが出ない。「追跡しない」方針と矛盾しない唯一の手段。

**所有権確認は HTML ファイル方式**を使う。`github.io` は Public Suffix List に載っているため
ドメインプロパティ（DNS認証）は作れず、URLプレフィックスプロパティで登録する。

1. Search Console で「URLプレフィックス」を選び `https://hikaclaude.github.io/damtabi/` を入力
2. HTMLファイル方式の `googleXXXX.html` をダウンロード
3. **`docs/` 直下に置いて** commit → push（`build_site.py` は `index.html` / `manifest.json` /
   `sitemap.xml` / `robots.txt` しか書かないので消えない。`.gitignore` にも掛からない）
4. Pages のビルド完了後に「確認」
5. 「サイトマップ」に `sitemap.xml` を送信（25URL）

metaタグ方式を使いたい場合は、`site.json` の `google_site_verification` に content の値を入れて
`build_site.py` を実行すれば `docs/index.html` に出力される（空なら何も出さない）。

見えるようになるのは、検索クエリ別の表示回数・クリック数・平均掲載順位、ページ別の同データ、
インデックス登録状況とエラー、モバイルユーザビリティ、被リンク。すべて Google 側の集計。

### PWA

`manifest.json` と `sw.js` を用意してあり、ホーム画面に追加できます。

- アイコン：192 / 512 / maskable 512 / apple-touch 180 と SVG
- Service Worker の原則は**「貯水率が載っているものは必ずネットワーク優先」**です。
  貯水率は JSON だけでなく**静的HTMLにも埋まっている**ので、
  HTML もキャッシュ優先にすると古い値を現在値として見せてしまいます。そのため
  **`data/*.json` と HTML ページは両方ネットワーク優先**、
  CSS / JS / 画像 / アイコンだけキャッシュ優先にしています。
- 通信できずキャッシュを返すときは、必ず古いと分かるようにします。
  - JSON … `stale` フラグを立て、地図の見出しに「オフライン: 保存済みの内容を表示中」
  - HTML … `<!--STALE-SLOT-->` を警告バーに差し替えて
    「オフラインのため、端末に保存された内容を表示しています」と表示

## 古い値を現在値に見せないための仕組み

このアプリで最も壊してはいけないところです。**手動更新なので更新が数日空きます。**
そのぶんここを厚くしてあります。

### 4層で守る

1. **欠測・未提供は埋めない**（バッチ）。前回の JSON を読まないので、値の流用が構造的に起きません。
2. **「いつの値か」を数値のすぐ下に必ず出す**。閾値はありません。常に出ます。
   - JS なしでも本文に `2026年9月4日 21:10 観測の値です（このページの生成: … JST）` と書いてあります
   - JS が動けば `（約3日前の観測値です）` という**経過日数**が加わります
3. **通常の更新リズムを超えたら段階的に注意を強める**（下記）。
4. **オフラインキャッシュは古いと明示する**（Service Worker）。

### 警告を出す日数と、その根拠

`site.json` の `freshness` で設定します。既定は **注意 7日 / 警告 14日**です。

| 経過 | 表示 |
|---|---|
| 常時 | 観測日時＋経過日数（例: 約3日前の観測値です） |
| **7日**以上 | 橙の注意「最新の貯水率は変わっている可能性があります」＋川の防災情報へのリンク |
| **14日**以上 | 赤の警告「大きく変わっている可能性があります」＋同リンク |

**なぜ 24 時間ではなく 7 日にしたか。**

最初は 24 時間で警告を出していましたが、手動運用では数日空くのが常態です。
**通常運用のたびに警告が出ると、利用者は警告を読み飛ばすようになります。**
そうなると本当に古いときにも効かなくなり、かえって原則を損ないます。

代わりに **経過日数そのものを閾値なしで常時表示**しました。
これで「黙って古い値を見せる」状態は日数によらず発生しません。
警告バーの役割は「値の開示」ではなく「通常の更新リズムを超えた」という一段上の合図に絞りました。

7日という数字は実測から決めています。手元の実測（室牧ダム、渇水期の低下局面）で
**利水貯水率は 9/1 の 68.1% から 9/4 に 60.8%、3日で 7.3ポイント（約 −2.4pt/日）**動きました。
この速さだと

| 経過 | 変化量の目安 |
|---|---|
| 3日 | 約 7ポイント |
| **7日** | **約 17ポイント** |
| 14日 | 約 34ポイント |

7日で約17ポイント。これは**このアプリの色分け1段ぶん**（80–95%、60–80%、40–60% はいずれも15〜20ポイント幅）に相当します。
つまり 7日経つと「地図上の色が変わっていてもおかしくない」水準です。注意を出す線として妥当と判断しました。
14日は約34ポイントで2段ぶん、これは警告に値します。

なお最上位の「95%以上」帯は5ポイント幅しかなく、この速さなら約2日で外れる計算です。
ただし帯の色分けは地図側の話で、静的ページが見せるのは日付つきの数値です。
そこは常時表示の経過日数でカバーしています。

**更新頻度を変えたら閾値も変えてください。** 毎日自動更新に戻すなら
`notice_days: 2 / warn_days: 5` あたりが目安です（`site.json` の1箇所）。
地図と静的ページは同じ設定値を見るので、基準がずれることはありません。

## 取得経路の選定

4 つの候補を実際に叩いて比較しました。結論は **「川の防災情報」の静的 JSON** です。

### 候補の比較

| 経路 | 利水貯水率 | 有効貯水率 | 形式 | 認証 | 判定 |
|---|---|---|---|---|---|
| **川の防災情報 静的 JSON** | ○ | ○ | JSON | 不要 | **採用** |
| www1.river.go.jp `DspDamData.exe` | △ 1 種のみ | × | EUC-JP の HTML | 不要 | 不採用 |
| dam.teraren.com API | ○ | ○ | JSON | **APIキー必須** | 不採用 |
| 富山防災WEB 実況表 | × | × | HTML | 不要 | 不採用 |

### なぜ「川の防災情報」の静的 JSON なのか

river.go.jp は Vue の SPA で、画面は JS 描画です。ただし**描画に使っている実データは
ただの静的 JSON ファイル**で、そこを直接読めば JS 実行なしで取得できます。

```
最新観測時刻  https://www.river.go.jp/kawabou/file/system/tmCrntTime.json
観測所マスタ  https://www.river.go.jp/kawabou/file/files/master/obs/dam/{obsFcd}.json
時系列データ  https://www.river.go.jp/kawabou/file/files/tmlist/dam/{YYYYMMDD}/{HHmm}/{obsFcd}.json
```

`obsFcd` はサイトの `app.js` と同じ規則で組み立てます（13 桁）。

```
("0000"+ofcCd).slice(-5) + ("00"+itmkndCd).slice(-3) + ("0000"+obsCd).slice(-5)
ダムの itmkndCd は 7。例) 室牧ダム = ofc 4098 / obs 63 → 0409800700063
```

採用した理由は 4 つです。

1. **両方の貯水率が別フィールドで取れる唯一の無認証経路**
   `storPcntIrr`（貯水率利水容量）と `storPcntEff`（貯水率有効容量）が独立して入っています。
2. **欠測と未提供を機械判定できる**
   各値に `*Ccd`（品質コード）が付きます。サイトの `app.js` と同じ規則で解釈しています。
   `190` = 欠測、`140` = 閉局、`130 以上または null` = その観測所では未提供、それ未満 = 有効な値。
   **推測せずに「取れない理由」を出せる**のはこの経路だけでした。この要件にとっては決定的です。
3. **JSON なのでスクレイピングより壊れにくい**
   HTML 構造の変更に影響されません。文字コードの問題もありません（UTF-8）。
4. **任意時刻を指定して取り直せる**
   `tmlist/dam/20260901/2020/...` のように過去のスロットも実在します（**約 1 か月**保持。
   8 日前は取得可、1 か月前は 404 を確認）。最新スロットが未生成のときに 10 分ずつ遡れるので、
   「一時的にファイルが無いだけ」を「欠測」と誤って記録せずに済みます。

なお river.go.jp の JS には `location.origin + "/api"` を叩く REST 実装も残っていますが、
本番では全て 404 でした（`Cannot GET /kwb/api/...`）。使われていない実装なので採用していません。

### 落選した経路の理由

**www1.river.go.jp（水文水質データベース）の `DspDamData.exe`**
現役で応答します（EUC-JP の HTML テーブル）。ただし返る貯水率カラムは**1 種類だけ**で、
利水と有効を併記できません。この要件（4 倍違うのでどちらかに丸めない）を満たせないので不採用。
HTML スクレイピング＋EUC-JP デコードが必要で、`.exe` CGI という壊れやすさもあります。

**dam.teraren.com**
API は `https://dam.teraren.com/api/v1/` に実在し、19 年分の履歴を持ち、利用は無償です。
ただし **Google サインインで発行する API キーが必須**で、認証情報なしのサーバレス日次バッチには
組み込めません。加えてサイト自身が「観測値のリアルタイム提供は行っていません」と明記しており、
出典も国交省の公開データです。**一次情報を直接取れるなら一次情報を取るべき**なので不採用。
ただし後述の平年値を作るときの有力候補なので、README に残しておきます。

**富山防災WEB（bousai.pref.toyama.jp）**
サーバレンダリングで扱いやすいのですが、実況表のカラムは
`ダム名 / 水系名 / 全流入量 / 全放流量 / 貯水位 / 洪水調節容量の各水位` で、
**貯水率も貯水量もありません**。掲載は県土木部管理の 16 基のみ（宇奈月・刀利・五位・臼中を含まない）。
このアプリの主目的を満たせないので不採用。

**第三者の個人サイト**
方針どおりスクレイピング対象にしていません。

## ピンの色分けと閾値の設計

### 問題

利水貯水率を等分割（0-33 / 34-66 / 67-100 など）で塗ると、ほとんどが同じ色になります。
実測（2026-09-04 20:30 時点、値が取れた 15 基）でも **6 基がちょうど 100.0%**、
99.2% を足すと **7 基が最上位バケットに集中**します。

### 原因は運用であって、データの不備ではない

観測所マスタの `lmtStg1`（洪水期制限水位）と運用期間を突き合わせると理由が見えます。
洪水期のダムは、洪水にそなえて水位を制限水位まで下げて運用します。このとき

- **利水容量**（利水のために確保する下側の容量）は満杯 → 利水貯水率 **100%**
- **有効容量**（利水容量＋洪水調節容量）は上側が意図的に空 → 有効貯水率は**低い**

という状態が「正常」になります。大谷ダムが典型で、制限水位 143.6 m に対して実測 143.71 m、
結果は**利水 100.0% / 有効 5.2%（約 19 倍差）**。CSV の備考「有効貯水率が極端に低い」は
故障ではなく設計どおりの運用状態です。

つまり **2 つの貯水率は別のことを測っている**ので、片方に丸めてはいけません。

- 利水貯水率 = **使える水がどれだけ残っているか**（渇水の指標）
- 有効貯水率 = **容量全体のうちどれだけ埋まっているか**（洪水期は低いのが正常）

### 平年値との乖離で色を決める案について

検討しましたが、**今回は採りませんでした**。

- 川の防災情報のマスタには基準値フィールド（`storPcntBs` / `storPcntEffBs`）がありますが、
  富山県の 20 基すべてで `null` でした。平年値は入っていません。
- 時系列 JSON の保持期間は**約 1 か月**で、平年値を作るには全く足りません。
- 19 年分の履歴を持つ dam.teraren.com は API キーが必要で、初版の前提（認証なし・サーバレス）に合いません。

**入手できない基準値をアプリ側で推定して色を決めるのは、このアプリの原則に反します。**
そこで固定閾値にしましたが、等分割ではなく次のように設計しました。

### 採用した閾値

**利水貯水率（既定）— 「満水からどれだけ目減りしたか」を見る非線形の刻み**

100% 付近が常態なので、上側を細かく、下側を粗く切ります。

| 区分 | 色 | 今日の該当数 |
|---|---|---|
| 95% 以上（ほぼ満水） | 青 `#1d4ed8` | 7 |
| 80–95% | 水色 `#0891b2` | 2 |
| 60–80% | 緑 `#15803d` | 2 |
| 40–60% | 橙 `#ea9a1a` | 2 |
| 40% 未満（少ない） | 赤 `#dc2626` | 2 |

7 / 2 / 2 / 2 / 2 に分かれ、5 色すべてが実際に使われます。
「95% 未満に落ちたら目に留まる」という、渇水の指標としての意味も持たせています。

**有効貯水率（切替可）— 実分布に合わせた刻み**

実測レンジが 2.0–51.6% と低い側に寄るので、閾値も低い側に寄せます。

| 区分 | 色 | 今日の該当数 |
|---|---|---|
| 60% 以上 | 青 | 0 |
| 40–60% | 水色 | 2 |
| 25–40% | 緑 | 6 |
| 10–25% | 橙 | 5 |
| 10% 未満 | 赤 | 2 |

**データなし**は色ではなく**斜線ハッチのグレーピン**にして、値が低いのか無いのかを取り違えないようにしています。

### 誤読を防ぐための表示

洪水期にあたるダムでは、詳細パネルに

> 現在は洪水期（03/21〜11/30）。洪水にそなえて水位を制限水位（143.6m）まで下げて運用するため、
> 利水貯水率が高くても有効貯水率は低く出ます。異常ではありません。

と出します。運用期間はマスタの `lmtStgStrt1` / `lmtStgEnd1` から取っています。

閾値は `scripts/fetch_dams.py` の `THRESHOLDS` に定義され、`dams.json` に書き出されます。
**SPA は自分で閾値を持たず JSON を読むだけ**なので、変更は 1 か所で済みます。

## イラストの差し込み

カードイラストは **1 箇所に登録するだけ**で、地図・静的ページ・OGP の 3 か所に反映されます。

### 1. 画像を置く

```
docs/img/dams/toyama-unazuki.png
```

**ファイル名はダムID（`dams.json` の `id`）と同じ英数字**にしてください。
サイズは **3:2**（900x600 以上を推奨）。png / jpg / webp が使えます。

> **日本語ファイル名でも動作します**（配信・相対パス解決・OGP生成すべて確認済み）。
> それでも英数字を推奨する理由は次の 3 つです。
>
> 1. URL では `%E5%AE%87...` のようなパーセントエンコードになり、
>    ログやSNSのデバッガで何の画像か読めない
> 2. Windows / macOS / Linux で濁点の正規化（NFC / NFD）が食い違い、
>    「ローカルでは出るのに GitHub Pages で 404」が起きうる
> 3. ダムID と同じ名前にしておけば、`illustrations.json` を見なくても
>    どのダムの画像か一目で分かり、OGP の出力ファイル名とも揃う

### 2. `docs/data/illustrations.json` に登録する

キーは **ダムID**、値は **`docs/` ルート基準のパス**です。

```json
{
  "toyama-unazuki": "./img/dams/toyama-unazuki.png"
}
```

パスは必ず `./img/dams/...` の形で書いてください。
ダムページは 3 階層下にあるため、ビルド時に `../../../img/dams/...` へ自動変換されます。

（キーにはダム名も使えますが、改名の影響を受けないIDを推奨します）

### 3. 反映する

```bash
python scripts/build_site.py    # 静的ページに反映
python scripts/make_images.py   # OGP画像を作り直す
```

地図画面は `illustrations.json` を実行時に直接読むので、再ビルド不要です。

### 反映先

| 反映先 | 使われ方 |
|---|---|
| 地図の詳細パネル | 上部のイラスト枠 |
| ダムごとの静的ページ | 同じくイラスト枠 |
| OGP 画像 | 3:2 から 1200x630 を `object-fit: cover` で切り出し、ダム名・水系・所在地を重ねて自動生成 |

`illustrations.json` はバッチが上書きしません。**貯水率を再取得してもイラストの割り当ては消えません。**
未登録のダムは、これまでどおり汎用の OGP カードと「イラスト準備中」のプレースホルダになります。

## 集水域（流域）の表示 — 第1段階まで完了・公開はしていない

「このダムに水が集まってくる範囲」を面で見せる機能。**データは作ったが、まだ表示していない。**
[国土地理院への照会](inquiry/gsi-elevation-derivative.md)の回答が出るまで第2段階（表示）に進まない。

### 方式

国土数値情報の流域界（W07 流域メッシュ）は使えなかった。富山県では収録が部分的で
（神通川水系は92km²分のみ）、単位も「単位流域」のためダムの集水域にならない。23基のうち7基は
ダム地点にメッシュ自体が無かった。

そこで**国土地理院の標高タイル**（`dem` = DEM10B、登録不要、地図タイルと同じ配信）から
地形解析で求めた。窪地埋め → D8流向 → 上流セル抽出 → 外周のポリゴン化 → 30m簡略化。
`scripts/build_basins.py`（単発実行、依存は numpy のみ）。

出力は `data/basins/`（**docs/ の外なので公開されない**）。GeoJSON 151.5KB / 23基 / 7,175頂点。
計算は全23基で約8分、標高タイル約1,000枚。

### 誤差は「合計」ではなく「直接流域」と比べる

**これが今回いちばん重要な発見。** 地形計算は導水（他の河川からの取水）を再現できないので、
ダム便覧の**直接流域面積**と比べるのが正しい。

| ダム | 便覧 合計 | 便覧 直接 | 便覧 間接 | 算出値 |
|---|---|---|---|---|
| 有峰ダム | 219.9 | 49.9 | **170.0** | 55.9 |
| 室牧ダム | 128.3 | 85.2 | **43.1** | 84.2 |
| 黒部ダム | 188.5 | 184.5 | **4.0** | 181.2 |

合計と比べると有峰は −77% の大外れに見えるが、直接流域と比べれば +11.9%。
**計算が正しいことと、導水判定が正しいことを同時に裏付けている。**

したがって表示では「**地形上の集水域**」と呼び、「流域面積」とは呼ばない。両者は別物。

### 精度（直接流域比）

| | 基数 |
|---|---|
| ±5%以内 | 16 |
| ±5〜15% | 3（和田川 −11.4%、有峰 +11.9%、白岩川 −6.5%） |
| **15%超** | **2（境川 −38.7%、臼中 −37.6%）** |
| 比較不可 | 2（舟川・大谷。ダム便覧に記載を確認できず） |

### 表示時に必ず書くこと（第2段階の要件）

1. **全ダム共通**：「地形から計算した概略の集水域です。実測の流域界ではありません」
2. **導水のある3基**（有峰・室牧・黒部）：「他の河川からも導水しているため、
   図の範囲は地形上の集水域であり、実際に水が集まる範囲とは異なります」
3. **境川・臼中**：「公式値と大きく異なります。原因は特定できていません」
   - 臼中はさらに「公式値自体が出典間で食い違っています（ダム便覧 13.5km² / 川の防災情報 48.2km²、3.5倍差）」
4. **舟川・大谷**：「公式の流域面積を確認できていないため、誤差を検証できていません」
5. 面積の誤差範囲を各ダムに表示する

分からないことを分からないと書く方針を、ここにも適用する。

### 実装中に直した3つの不具合（同じ罠を踏まないため）

1. **河道スナップの半径を固定にしていた** — 250m固定だと刀利ダムが−99.7%（河道に届かず1セル）、
   500mにすると角川ダムが+724%（隣の大きな川に飛ぶ）。小さい半径から試し、公式面積と桁が
   合った時点で採用する方式に変更。公式面積は「どの河道に乗せるか」の判定にのみ使い、
   結果の値には手を加えていない。
2. **範囲を広げて再計算するときスナップし直していた** — 格子を広げると流向場が変わり、
   スナップ先が別の川へ移る。**出口セルを緯度経度で固定**し、拡大後は同じ地点を使う。
3. **「面積が合っていれば拡大しない」ガードを入れたら逆効果だった** — 宇奈月ダムなど
   大流域で必要な拡大まで止まり −12.5% になった。2 の修正で不要になったため撤去。

## 独自ドメインへの移行

将来 `damtabi.jp` などを取得したときの手順です。**手順どおりにやれば移行できます。**
（2026-09-05 時点で damtabi.jp / .com / .net / .org / .app はいずれも未登録でした）

### 手順

**1. ドメインを取得し、DNS を設定する**

apex ドメイン（`damtabi.jp`）で公開する場合、DNS に GitHub Pages の A / AAAA レコードを設定します。

```
A     @   185.199.108.153
A     @   185.199.109.153
A     @   185.199.110.153
A     @   185.199.111.153
AAAA  @   2606:50c0:8000::153
AAAA  @   2606:50c0:8001::153
AAAA  @   2606:50c0:8002::153
AAAA  @   2606:50c0:8003::153
```

`www.damtabi.jp` を使う場合は CNAME を `hikaclaude.github.io.` に向けます。
（上記IPは GitHub の公式ドキュメントで最新を確認してください。変わることがあります）

**2. `site.json` の `base_url` を書き換える** ← コード側の変更はここ 1 行だけ

```json
{ "base_url": "https://damtabi.jp", ... }
```

末尾スラッシュは付けません。サブディレクトリが無くなる点に注意
（`https://hikaclaude.github.io/damtabi` → `https://damtabi.jp`）。

**3. CNAME ファイルを置く**

GitHub Pages はリポジトリ内の `CNAME` ファイルで独自ドメインを認識します。
公開ディレクトリが `docs/` なので、置き場所は **`docs/CNAME`** です。

```bash
echo "damtabi.jp" > docs/CNAME
```

改行以外は入れず、1行だけ。**サブドメインを含む完全なホスト名**を書きます（`https://` は不要）。

> **注意**: GitHub の Settings → Pages 画面で独自ドメインを設定すると、GitHub が
> `docs/CNAME` を**自動でコミットします**。手で作った場合と二重にならないよう、
> どちらか一方（画面設定 or ファイル）に統一してください。おすすめは
> **先に `docs/CNAME` をコミットしてから Settings で確認する**順です。
>
> また `CNAME` は `build_site.py` が触りません。再ビルドで消えることはありません。

**4. 再ビルドして push**

```bash
python scripts/build_site.py   # canonical / og:url / og:image / sitemap / robots / manifest が追随
git add -A && git commit -m "chore: 独自ドメインへ移行" && git push
```

**5. HTTPS を有効にする**

Settings → Pages → **Enforce HTTPS** にチェック。証明書の発行に数分〜1時間かかります。
チェックできない間は DNS の伝播待ちです。

**6. 確認**

```bash
curl -sI https://damtabi.jp/ | head -1
curl -s https://damtabi.jp/ | grep -o '<link rel="canonical"[^>]*>'
curl -s https://damtabi.jp/robots.txt
```

canonical と sitemap が新ドメインになっていること、`/dam/toyama/unazuki/` が開くことを確認します。

### 旧URLからどうつなぐか

**GitHub Pages が自動でリダイレクトします。** 独自ドメインを設定すると、
`https://hikaclaude.github.io/damtabi/...` へのアクセスは
対応するパスの `https://damtabi.jp/...` へ **301 リダイレクト**されます。
パス構造は変えないので、`/dam/toyama/unazuki/` のような個別ページもそのまま引き継がれます。

**したがって、リダイレクト用のファイルを自分で用意する必要はありません。**
このために URL 設計を `/dam/{都道府県}/{読み}/` で固定してあります。

移行後にやること:

1. **Search Console に新ドメインのプロパティを追加**し、`https://damtabi.jp/sitemap.xml` を送信
2. 旧プロパティ（`hikaclaude.github.io/damtabi`）は消さずに残す。301 が認識され、
   評価が新ドメインへ引き継がれるまで数週間かかります
3. **OGP のキャッシュを更新**。SNS は URL 単位で画像をキャッシュするので、
   各プラットフォームのデバッガで新URLを再取得させます
4. 告知済みのリンクがあれば新URLに差し替える（301 が効くので急ぎではありません）

### やってはいけないこと

- **`base_url` を変えずにドメインだけ切り替える**。canonical が旧URLのまま残り、
  検索エンジンは「新URLは旧URLの複製」と判断します。必ず `site.json` → 再ビルド → push の順で。
- **`docs/CNAME` を消す**。消すと独自ドメインが解除され、リダイレクトも止まります。
- **URL 構造を同時に変える**。ドメイン移行とパス変更を一度にやると、
  何が原因で順位が落ちたか分からなくなります。分けて行ってください。

### 独自ドメインにすると得られるもの（移行の判断材料）

URL が短くなるだけではない。**アクセス数の把握方法が変わる**のが実質的に大きい。

GitHub Pages は**アクセスログを提供しない**ので、いま利用状況を知る手段は
Google Search Console（＝Google検索経由の表示回数とクリック数）だけになる。
サイトに計測コードを置けば数えられるが、**利用者の端末から外部へリクエストを出す**ことになり、
「追跡しない」という方針と合わないため採用していない（GoatCounter 等も同じ理由で見送り）。

独自ドメインにして Cloudflare 経由で配信すると、**サーバ側で集計されるため
計測コードも Cookie も不要**になる。利用者の端末からは追加のリクエストが一切出ない。
これは方針と矛盾しない唯一の全アクセス把握手段なので、移行時に検討する。

### Organization へ移す場合（将来の選択肢）

`damtabi-lab` のような Organization に移管する場合も、**独自ドメインを先に当てておけば
公開URLは変わりません**（`https://damtabi.jp` のまま）。
リポジトリ移管時に GitHub Pages の設定と `docs/CNAME` を再確認するだけで済みます。
**独自ドメインを先に取る方が、後の移管が楽になります。**

## バッチの挙動

- 出力は毎回まっさらに作り直します。**前回の JSON は読みません**（値の使い回しを構造的に不可能にするため）。
- 最新スロットが未生成のときは 10 分ずつ最大 6 回遡って探します。
- HTTP エラーは 3 回までリトライ（404 は即中断）。すべて失敗したら `fetch_failed` として理由付きで記録し、
  **他のダムの処理は続行**します。1 基の失敗で全体を落としません。
- リクエスト間に 0.3 秒空けています（1 回の実行で約 50 リクエスト）。
- マスタが取れなくても実測値の取得は続行します（洪水期の注記が出ないだけ）。

```
[fetch_dams] 基準観測時刻 2026/09/04 20:30
  宇奈月ダム     利水=87.6%      有効=20.2%      [ok] 2026/09/04 20:30
  熊野川ダム     利水=—(missing) 有効=—(missing) [missing] 2026/09/04 20:20
  刀利ダム      利水=—(not_provided) 有効=—(not_provided) [not_provided] 2026/09/04 20:20
  黒部ダム      利水=—          有効=—          [no_source]
[fetch_dams] 内訳 {'ok': 15, 'missing': 2, 'not_provided': 3, 'no_source': 3}
```

## 全国展開に向けたメモ

この初版は富山県 20 基で全工程を一周させることが目的ですが、選んだ経路はそのまま全国に伸びます。

- `obsFcd` の組み立て規則は全国共通です。都道府県コードから市町村一覧
  （`obslist/idx/pref/twn/{prefCd}.json`）→ 市町村ごとの観測所一覧
  （`obslist/obs/twnlist/{twnCd}.json`）とたどれば、**ダム一覧を CSV 手入力なしで自動生成できます**。
  富山県（prefCd 1601）でこの経路を実際に使って、CSV の 20 基と完全一致することを確認済みです。
- 閾値は全国だと分布が変わるはずなので、`THRESHOLDS` の見直しが要ります。
  平年値を使う案は、履歴データ源（dam.teraren.com など）を確保できた時点で再検討するのが良いと思います。
- 発電専用ダムの「データ提供なし」扱いは全国でも多数出ます。`toyama_dams_nodata.csv` と
  同じ形で県ごとに持てば拡張できます。
